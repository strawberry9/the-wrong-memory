Introduction

The Wrong Memory

The objective of this book is to develop a particular way of understanding memory-safety bugs in the C programming language. For the purposes of this book, memory safety concerns whether accesses remain valid with respect to objects, bounds, storage, and lifetimes.

C emerged from a design context in which direct manipulation of machine resources was a feature rather than an anomaly. Its relatively low-level memory model permits programmers to manipulate objects through pointers and pointer arithmetic, without generally enforcing at the language level that each resulting access remains within the bounds and lifetime of the object concerned.[1][2]

This book demonstrates how memory-safety problems can arise from C's design decisions, particularly where they leave important relationships between values, objects, bounds, locations, and lifetimes to be maintained by the programmer.

In C, these elements interact through a chain of dependencies. A wrong size can produce an undersized allocation; pointer arithmetic can then produce a pointer outside that allocation; and a subsequent copy can overrun the object. The resulting corruption may remain hidden until much later, when its original cause is difficult to trace.

There is a simple sentence that captures a recurring pattern in many serious C memory bugs: 

I calculated, addressed, allocated, copied, or freed the wrong amount or location of memory.

The central idea of this book is that memory bugs are often chains of incorrect assumptions rather than isolated mistakes, and that understanding them requires following those chains rather than examining each operation in isolation.

The memory chain

Memory-safety bugs in C are often described using categories such as: 

integer overflow
buffer overflow
out-of-bounds access
use-after-free
double free
memory corruption

These categories are useful for describing failures, but they can hide the relationships between them. A vulnerability may begin as an error in one part of a program and become visible only after that error has propagated through several subsequent operations.

Consider a program that receives a count, calculates a size from that count, allocates memory, walks through the resulting object, and eventually copies data into it.

The count might be wrong.

The calculation might be wrong.

The allocation might be too small.

The pointer might be calculated from the wrong value.

The bounds might be wrong.

The copy might be too large.

The object might no longer exist.

The eventual failure may therefore occur several steps away from the original mistake.

A useful starting point for following such a failure is: 

integer arithmetic
    ->
allocation size
    ->
pointer arithmetic
    ->
bounds
    ->
memory corruption

This is not a rigid sequence. Real programs may skip steps, repeat them, or introduce other operations between them. The memory chain is a way of thinking about the dependencies that connect one operation to the next.

When a number is used to describe memory, we should ask where that number came from.

When an address is calculated, we should ask what object it is intended to identify.

When memory is allocated, we should ask what logical object the allocation is supposed to contain.

When a range is accessed, we should ask why the program believes that range is valid.

And when memory is freed, we should ask whether the pointer still identifies the intended object.

The answers to these questions form a chain of reasoning.

From code to assumptions

C code often looks deceptively local. Consider: 

size = count * element_size; // Calculate the total number of bytes needed
char *p = malloc(size);       // Allocate that amount of memory
char *q = p + offset;         // Compute a new pointer
memcpy(q, src, length);       // Copy length bytes to that location

Each statement is short. The interesting question is not whether each statement looks reasonable by itself. It is whether the assumptions connecting them are true.

What does count represent?

What does size represent?

What object does p point to?

What does offset measure?

What is the relationship between length and the remaining space?

The answers to these questions turn a collection of statements into a chain of reasoning. They require us to identify the invariants that connect the operations and to treat the code as a logical proof that memory is being allocated and addressed correctly.

A memory-safety bug occurs when an assumption required for that proof no longer holds.

The wrong amount and the wrong location

The phrase at the heart of this book has two particularly important dimensions: 

amount

and: 

location

A program can use the correct location but the wrong amount of memory. It can use the correct amount but the wrong location. It can get both wrong.

These cases lead to different manifestations, but the underlying question is the same: 

What memory did the programmer believe this operation referred to,
and what memory did it actually refer to?

That question is often more useful than simply asking which bug category applies.

Why follow the chain?

Suppose a program crashes during a copy.

The copy may be where the problem becomes visible, but it may not be where the problem began.

Perhaps an input value was converted incorrectly.

Perhaps an arithmetic calculation overflowed.

Perhaps an allocation was therefore too small.

Perhaps a later pointer calculation still used the original logical size.

Perhaps the copy finally crossed the physical boundary of the allocation.

Looking only at the final copy tells us what went wrong at the end of the chain. Following the chain tells us why.

That distinction matters both for debugging and for security. It determines whether we merely patch the operation that happened to fail or repair the assumption that made the failure possible.

A way of reading C

The chapters that follow use this idea as a recurring method of analysis. We will not treat integer arithmetic, allocation, pointers, bounds, and memory corruption as unrelated topics. Instead, we will follow values as they move through a program.

A value may begin as: 

input

become: 

count

then: 

size

then: 

allocation

then: 

offset

then: 

address

and finally: 

memory access

At each stage, the program makes an assumption about what that value means. Our job is to determine whether the assumption remains true.

This approach also explains why apparently minor C details can become security vulnerabilities. A small numerical mistake is not necessarily dangerous by itself. It becomes dangerous when the resulting value is trusted to describe memory.

The question to keep asking

Throughout the book, when you encounter code that manipulates memory, return to the same statement: 

I calculated, addressed, allocated, copied, or freed the wrong amount or location of memory.

Then ask: 

Which one?

Where?

Based on which value?

Calculated how?

Relative to which object?

And what happens next?

Those questions are enough to begin tracing many difficult memory bugs. The chapters that follow fill in the technical details.

The goal is not to memorize a longer list of dangerous C constructs. It is to develop a way of seeing the relationships between numbers, objects, addresses, and memory.

Once those relationships become visible, many apparently different C memory vulnerabilities start to look like variations of the same problem: 

the program believed it was operating on one region of memory,
but the calculation, address, allocation, copy, or lifetime
described another.

That is the wrong memory.

Who Is This Book For?

The Wrong Memory is primarily about learning how to reason about C memory-safety problems: not just recognising a vulnerability, but understanding the assumptions that led to it.

It is written for C and systems programmers, security engineers, code reviewers, students, and others interested in how memory-safety failures arise.

C and systems programmers

If you write C, you will probably recognise many of the individual problems discussed here: integer overflow, buffer overflow, out-of-bounds access, use-after-free, double-free, and so on.

The book's focus is not on introducing new categories of bugs, but on showing how they are connected. A value can determine a size, a size can determine an allocation, an allocation can determine a valid range, and that range can determine a memory operation. When one of the assumptions in that chain becomes false, the eventual failure may occur much later.

The book provides a framework for tracing those relationships.

Security engineers and code reviewers

The same approach can be useful when investigating unfamiliar code. Instead of asking only whether an expression looks dangerous, the book encourages questions such as:

  • What controls this memory operation?
  • What is that value supposed to mean?
  • What assumptions must hold?
  • Where is the first assumption violated?
  • How does that error reach memory?

The goal is to understand the path from the original mistake to the eventual vulnerability.

Students and experienced programmers

The book assumes some familiarity with C, pointers, arrays, structures, and dynamic allocation. It is therefore not a beginner's introduction to C, but neither does it require experience in vulnerability research.

For experienced programmers, many individual rules and examples will be familiar. The intended value is in considering them together as a common model of memory safety.

What this book is not

The Wrong Memory is not an exhaustive reference to C semantics, a catalogue of real-world vulnerabilities, or an exploit-development manual. Its purpose is narrower: to provide a coherent way of thinking about why memory-safety failures occur and how apparently different failures can be related.

The question at its centre is:

What did the program believe about memory, and where did that belief stop being true?

A Brief Outline of the Book

Part I: Following the Chain

Part I mirrors the pipeline of how a program prepares to interact with memory, tracing how an abstract number transforms into a structured target:

  • Chapter 1 (Integer Arithmetic): Explores how ordinary integer operations become memory-safety problems through signed/unsigned mismatches, wraparound, truncation, and flawed size calculations, separating a valid number from a valid size.
  • Chapter 2 (Allocation Size): Examines how that math becomes an object in memory via sizeof expressions, type conversions, undersized or oversized allocations, and recognizing when the allocator itself is innocent of the underlying sizing bug.
  • Chapter 3 (Pointer Arithmetic and Bounds): Details how allocated memory becomes addresses and ranges through array indexing, offsets, object boundaries, one-past-the-end pointers, and why possessing a valid pointer never guarantees a valid access.
  • Chapter 4 (From Bug to Vulnerability): Bridges ordinary programming errors to security impacts, analyzing how out-of-bounds reads and writes, data/metadata corruption, and control-flow consequences turn incorrectness into exploitability.

Part II: The Other Side of the Boundary

Part II pivots from preparation to execution, isolating mechanical failure points by looking closely at how memory is manipulated across ranges, boundaries, and locations:

  • Chapter 5 (Copying the Wrong Amount): Analyzes memory-copy operations (memcpy, memmove, memset) as range operations, investigating source/destination mismatches, overlapping regions, and how innocent copies become corruption primitives.
  • Chapter 6 (Reading the Wrong Amount): Focuses on unauthorized consumption beyond intended boundaries, addressing length fields, sentinel/terminator assumptions, missing bounds checks, and why out-of-bounds reads are dangerous even without data overwrites.
  • Chapter 7 (Writing the Wrong Amount): Explores stack and heap corruption, off-by-one errors, struct/array boundary violations, metadata overwrites, and why the object containing the bug is often entirely separate from the object that gets corrupted.
  • Chapter 8 (Addressing the Wrong Location): Examines cases where the allocated size is correct but the destination is wrong due to incorrect offsets, pointer provenance adjustments, NULL/near-NULL addresses, and misidentified objects.

Part III: Lifetime

Part III introduces the temporal dimension, moving beyond spatial boundaries to examine how objects age, expire, and get reclaimed across time:

  • Chapter 9 (Using Memory After Its Lifetime): Tackles temporal safety through use-after-free conditions, dangling pointers, stale aliases, reallocation traps, and how allocator reuse alters the nature of the corruption.
  • Chapter 10 (Freeing the Wrong Memory): Looks at invalid lifecycle operations, including double frees, invalid frees, interior pointer releases, ownership confusion, and error paths where cleanup logic goes awry.
  • Chapter 11 (The Complete Memory Operation): Brings all the threads together into unified synthesis, integrating complete operational chains, the five diagnostic questions, boundary proofs, modern defenses, and debugging strategies into a final, comprehensive review.

Appendices

The five appendices extend the ideas developed in the main chapters beyond the analysis of individual C vulnerabilities. They form a conceptual progression: the first examines how different languages can make memory safety a property of the language; the second develops the theory of semantic invariants that underlies the book's analysis; the third asks whether C itself can become meaningfully memory safe without ceasing to be C; the fourth considers what changes in the programmer's mental model when moving from C to Rust; and the fifth explores AI-assisted invariant analysis.

The appendices can be read independently, but they are intended to deepen the questions raised by the main chapters. Together, they move from how memory safety can be achieved, through why C fails to provide it, to whether C can change, to what it means for a programmer to adopt a different model of memory safety, and finally how AI can help programmers discover the "unknown unknowns" - the invariants that exist in the code but have never been explicitly written down, documented, or enforced.

  • Appendix I - Making Memory Safety a Property of the Language: Examines the different ways programming languages can make memory-safety guarantees explicit and enforceable, including garbage collection, bounds checking, ownership and borrowing, capabilities, contracts, formal verification, and explicit safe and unsafe boundaries.
  • Appendix II - A Theory of Semantic Invariants: Develops a formal model of semantic invariants and shows how it provides a common explanation for the causal relationships underlying different classes of C memory-safety vulnerabilities, from the first broken assumption to the eventual security consequence.
  • Appendix III - C may have reached the boundary of what its own design principles permit it to become: Examines whether the C language itself can acquire meaningful memory-safety guarantees while preserving the principles that govern its design and evolution, including simplicity, portability, compatibility, programming freedom, and C's existing programming model.
  • Appendix IV - The Psychological Transition From C To Rust: Examines the cognitive shift from C to Rust, focusing on how ownership, borrowing, mutation, aliasing, and lifetime change the way programmers represent and reason about program state.
  • Appendix V - AI and the Division of Cognitive Labour: Explores how AI can help programmers discover implicit invariants and make hidden assumptions visible.
