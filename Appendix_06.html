Preface

As argued throughout The Wrong Memory essays, attempting to tack a "safe subset" onto an inherently unsafe language usually fails because the core language semantics still allow invariant violations. By embedding ownership and borrowing into the core type system, CobaltC makes safety an intrinsic property of the language rather than an optional discipline imposed upon it.

CobaltC unashamedly draws on the ownership and memory-safety techniques demonstrated by Rust. Although Rust isn't the origin of most of these ideas, its significant contribution was demonstrating how they could be combined into a practical, high-performance systems language. CobaltC adopts that safety architecture without attempting to reproduce Rust's syntax or overall language philosophy. Instead, it applies the broader body of ideas to the problem identified in Appendix II: making semantic invariants such as ownership, lifetime, aliasing, mutability, and bounds properties that the compiler can represent and enforce, rather than obligations the programmer must maintain by convention.

1. Introduction

**This specification does not tell you how to implement something if it tells you unambiguously what a conforming implementation must do.

CobaltC is a statically typed systems programming language providing:

  • explicit ownership;
  • deterministic destruction;
  • compiler-checked borrowing;
  • inferred lifetimes;
  • explicit nullability;
  • bounds-safe operations;
  • structured error handling;
  • safe concurrency;
  • explicit unsafe operations;
  • explicit foreign-function interfaces.

The language is intended for software requiring predictable resource management, strong memory safety, native execution and controlled interaction with low-level facilities.

CobaltC specifies ownership, lifetime, destruction, and observable memory-safety behavior; it does not prescribe the implementation technique used to achieve them.

CobaltC does not prescribe a memory-management implementation. The implementation strategy is intentionally left to the implementor, provided that all normative language and safety guarantees are preserved.

CobaltC is C-like data + ordinary functions + generics + explicit memory/ownership safety + modules, without OO inheritance/interfaces/dynamic dispatch.

The CobaltC specification prioritizes semantic clarity over compilation determinism. It defines the contract of what memory safety looks like on paper, leaving the grueling mathematical and engineering implementation details as an exercise for anyone brave enough to build it.

2. Normative Terminology

The words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative.

Implementation-defined means that an implementation chooses the behavior and documents that choice.

Undefined behavior is behavior for which this specification imposes no requirements. Safe CobaltC operations MUST NOT introduce undefined behavior merely through ordinary use.

A CobaltC program consists of one or more source modules.

Source text is Unicode.

Whitespace separates lexical tokens where necessary and otherwise has no semantic meaning.

8. Modules

A module declaration has the form:

module example;

A module establishes a namespace.

Modules MAY import declarations, or selective declarations, from other modules: 

import io;
import io { print, println };

Name resolution is lexical and module-aware.

An unresolved name is a compile-time error.

Declarations describe implementation. A modules export { ... } block describes the module's external contract.

The export block applies only to declarations belonging to the module in which the block appears.

A submodule is a separate module and is not exported by its parent module.

If a module does not contain an export block, the module exports no declarations.

Inner declarations MAY shadow outer declarations where permitted.

A variable is declared using:

A mutable variable is declared:

An uninitialized declaration is permitted:

i32 result;

A constant cannot be mutated.

13. Compound Types

CobaltC supports:

  • structs
  • enums
  • arrays
  • function types
  • managed pointers (T* and T*?)
  • raw pointers (raw T*)
  • generic types

Structs and enums are nominal types.

Type aliases do not create new nominal types.

14. Managed Pointers

The notation:

T*

represents a managed, non-null pointer.

The notation:

T*?

represents a nullable managed pointer.

Managed pointers participate in ownership, borrowing, and lifetime checking.

15. Raw Pointers

Raw pointers are represented:

raw T*

Raw pointers are outside the ordinary managed ownership and lifetime guarantees.

Raw-pointer dereference and unrestricted pointer manipulation require an unsafe context.

16. Mutability

A mutable binding permits mutation through that binding where no ownership or borrowing rule prohibits the operation.

Mutability does not override aliasing rules.

For example, having a mutable owner does not permit mutation while an incompatible borrow remains active.

17. Type Compatibility

Assignments, function arguments and return values MUST have compatible types.

Implicit conversions MUST NOT silently:

  • remove nullability;
  • create ownership;
  • destroy ownership;
  • violate mutability;
  • invalidate a lifetime guarantee;
  • perform unsafe reinterpretation.

Explicit conversion facilities MAY be provided.

18. Type Inference

CobaltC permits inference where the language grammar and context establish a unique type.

Inference MUST preserve all semantic distinctions relevant to:

  • ownership;
  • mutability;
  • nullability;
  • borrowing;
  • lifetime.

Inference MUST NOT make an unsafe operation appear safe.

19. Generic Types and Functions

Generic types and functions are statically checked.

A generic type or function declaration defines a single type or function. Supplying type arguments produces a specialization of that declaration and does not define a separate type or function.

Example:

fn identity<T>(T value) : T { return value; }

identity<i32> and identity<f64> are specializations of the same identity function declaration.

20. Interfaces

CobaltC does not provide interfaces.

Types do not implement interfaces, and interfaces are not types, runtime values, or a mechanism for polymorphism.

CobaltC provides parametric polymorphism through generics, but does not provide subtype polymorphism, inheritance, or dynamic dispatch.

21. Structs

A struct defines a nominal aggregate: 

struct Point
{
    i32 x;
    i32 y;
}

Struct fields have declared types. A struct value owns its owned fields according to their declared types and the language's ownership rules.

Structs do not contain function declarations. Operations on a struct may instead be declared as associated functions using the struct's qualified name.

21.1. Destruction

A type may define an associated function named destroy that accepts a mutable managed pointer to the type: 

fn File::destroy(File* file)
{
    ...
}

The destroy function is the type's destruction operation. When an owning binding reaches the end of its lifetime, the compiler automatically invokes the associated destroy function for the value, if one is defined.

The compiler MUST invoke a type's destruction operation exactly once for each owned value. A value MUST NOT be automatically destroyed after its ownership has been transferred by a move.

When a type defines an associated destroy function, that function is solely responsible for destroying the value's owned resources. The compiler MUST NOT perform an additional automatic destruction pass over the value's fields after invoking the user-defined destroy function.

A destroy function may therefore delegate destruction to owned fields: 

struct Stack<T>
{
    Vector<T> values;
}

fn Stack<T>::destroy(Stack<T>* stack)
{
    Vector<T>::destroy(&mut stack->values);
}

When an owning Stack<T> binding reaches the end of its lifetime, the compiler invokes Stack<T>::destroy. The function destroys the owned Vector<T>, which in turn destroys its live elements and releases its backing storage.

Because Stack<T>::destroy is responsible for destroying values, the compiler does not subsequently destroy values a second time.

21.2. Structs Without Destruction Operations

A type does not require a destroy function merely because it is a struct. Fundamental value types such as i32, usize, and bool do not own resources requiring destruction.

A struct containing only fields that require no destruction therefore requires no user-defined destroy function: 

struct Point
{
    i32 x;
    i32 y;
}

mut Point point = Point
{
    x = 10,
    y = 20
};

When point reaches the end of its owning lifetime, no destruction function is invoked because neither Point nor its fields require destruction.

More generally, if a struct does not define destroy and contains fields whose types require destruction, destruction proceeds recursively according to the ownership of those fields. Each owned field requiring destruction is destroyed exactly once.

For example: 

struct Container<T>
{
    Vector<T> values;
}

mut Container<i32> container = Container<i32>
{
    values = Vector<i32>::new()
};

If Container<T> does not define its own destroy function, its owned Vector<T> field is destroyed according to the Vector's destruction operation.

21.3. Destruction and Move Semantics

Destruction follows ownership. After a value has been moved, the moved-from binding no longer owns the transferred value and therefore MUST NOT destroy that value. 

mut File a = open("data.txt");
File b = move a;

At the end of b's owning lifetime, the compiler invokes File::destroy for the transferred File. The moved-from binding a does not cause the same value to be destroyed again.

Ownership transfer, borrowing, and destruction MUST preserve the invariant that exactly one owner is responsible for each owned value. Destruction MUST NOT cause the same owned value to be destroyed more than once.

21.4. Destruction and Borrowing

An owning binding MUST NOT reach the end of its lifetime while a live managed borrow would remain valid only while that binding exists. The ownership, borrowing, and lifetime rules therefore prevent automatic destruction from invalidating a live managed pointer.

For example: 

mut Point point = Point
{
    x = 10,
    y = 20
};

i32* p = &point.x;

While p is a live managed borrow, the owning lifetime of point cannot end. The compiler MUST reject any program in which destruction of point would invalidate a live managed pointer.

21.5. Destruction and Nested Ownership

Destruction of nested values follows the ownership hierarchy. For example: 

struct File
{
    raw i32 handle;
}

fn File::destroy(File* file)
{
    close(file->handle);
}

struct Document
{
    File file;
    i32 line_count;
}

If Document does not define a destroy function, its owned File field is destroyed and its i32 field requires no destruction.

If Document defines its own destroy function, that function becomes responsible for destroying its owned resources: 

fn Document::destroy(Document* document)
{
    File::destroy(&mut document->file);
}

The compiler invokes Document::destroy exactly once when an owning Document binding reaches the end of its lifetime. The compiler does not additionally invoke File::destroy for file.

This rule allows destruction to remain explicit and predictable while permitting complex owning types to compose simpler owning types.

22. Enums

An enum defines a finite set of named variants: 

enum Status
{
    Ready,
    Running,
    Failed
}

Variants MAY contain associated values: 

enum Result<T,E>
{
    Ok(T),
    Err(E)
}

Enum variants are part of the enum's semantic interface. A variant MAY be used to construct a value of the enum, and enum values MAY be pattern-matched by their variants.

For example, Ok(value) constructs a Result<T,E> containing a value of type T, while Err(error) constructs a Result<T,E> containing a value of type E. A variant constructor is not an ordinary function, although it behaves similarly to a constructor operation for the purposes of type checking and value construction.

When an enum type is exported, its variants are part of the externally usable interface of that enum. Exporting an enum does not, however, expose its physical representation. External code MUST NOT inspect or manipulate the enum's discriminator, layout, storage, or other representation details unless those details are explicitly exposed by a language mechanism defined by this specification.

23. Tuples

Tuples are not a part of CobaltC.

CobaltC deliberately avoids tuples in favor of named structures and other explicitly defined types. While tuples provide a convenient way to group a small number of values, they introduce an additional kind of anonymous, positional type into the language.

Instead of defining a type such as: 

(Int, String, Bool)

CobaltC encourages the use of a named structure: 

struct Result
{
    Int value;
    String message;
    Bool success;
}

This keeps the meaning of data explicit and avoids relying on positional fields such as .0, .1, and .2.

The absence of tuples also keeps the language's type system and syntax smaller and more consistent. When multiple values conceptually belong together, CobaltC prefers that relationship to be represented by an explicit type rather than an anonymous tuple.

24. Arrays

Arrays contain a fixed number of elements: 

T[N]

The length is part of the array type.

Safe indexing MUST remain within the valid range.

25. Functions

A function is declared by specifying its name, parameters, and, optionally, its return type: 

fn add(i32 a, i32 b) : i32
{
    return a + b;
}

If the : and return type are omitted, the function has a return type of void: 

fn log(String message)
{
    print(message);
}

An explicit void return type is also permitted: 

fn log(String message) : void
{
    print(message);
}

A function MAY be associated with a type using a qualified name: 

struct Stack<T>
{
    Vector<T> values;
}

fn Stack<T>::new() : Stack<T>
{
    return Stack<T>
    {
        values = Vector<T>::new()
    };
}

An associated function is identified by the pair consisting of its associated type and function name.

An associated function may then be referenced through either its type or a value of that type.

Associated functions are ordinary free functions that provide type-oriented organization and lookup without introducing this, self, implicit receivers, or object-oriented method dispatch.

Type qualification selects the associated function; the function's declared parameter list determines what arguments must be supplied.

The number and types of arguments MUST match the function signature.

A function with a return type other than void MUST return a value compatible with its declared return type. A void function MUST NOT return a value.

Ownership and borrowing requirements apply to arguments and return values.

Function names MUST NOT be overloaded within the same lookup scope. A function declaration introduces a single function identified by its name and, for associated functions, its associated type and name. Parameter types are not used to select between functions with the same name.

28. Arithmetic

Integer and floating-point operations follow the semantics of their respective types.

An operation that cannot safely produce the required result MUST follow the type's specified overflow or failure semantics.

Safe arithmetic MUST NOT silently produce memory corruption.

29. Equality

Equality requires compatible operands.

Value equality compares values according to the type's equality semantics.

Where pointer identity is explicitly requested, pointer equality compares identity rather than recursively comparing referents.

30. Assignment

Assignment requires a valid mutable destination.

Compound assignment follows the corresponding arithmetic or bitwise operation.

Assignment does not implicitly transfer ownership unless the operation constitutes a move.

31. Function Calls

A call is valid only if:

  • the function is resolvable;
  • the argument count is correct;
  • arguments have compatible types;
  • ownership transfers are valid;
  • borrows remain valid;

CobaltC provides:

    ...

33. Loops

CobaltC provides: 

while
for
loop

break exits the applicable loop.

continue begins the next iteration.

34. Match

Pattern matching is provided by match. A match may be used as either a statement or an expression.

Example:

match value { Some(x) => use(x), None => use_default() }

A match expression may produce a value:

String result = match value { 1 => "one", 2 => "two", _ => "other" };

A match over an exhaustively known variant set MUST handle every possible case.

The compiler MUST reject statically non-exhaustive matches.

Match arms are evaluated in source order and the first matching arm is selected.

The _ pattern matches any value not matched by an earlier arm.

35. Return

return transfers control from the current function.

Returning an owned value transfers ownership to the caller.

Returning a managed pointer is permitted only if its lifetime remains valid after the function returns.

A managed pointer to an ordinary local variable MUST NOT be returned.

36. Defer

defer registers a block to be executed when the enclosing scope is exited: 

fn update_shared_state(Mutex* mutex)
{
    Lock lock = Mutex::lock(mutex);
    defer { Lock::unlock(&lock); }

    modify_shared_state();
}

Deferred blocks execute in reverse registration order.

Deferred blocks execute before owned locals in the exited scope are destroyed.

Deferred operations themselves obey the ordinary ownership and lifetime rules.

37. Definite Initialization

A value MUST be initialized before it is read.

The compiler MUST perform control-flow-sensitive definite-initialization analysis.

This is invalid: 

i32 value;

if condition
{
    value = 10;
}

print(value);

unless the compiler can prove that every path reaching print initializes value.

38. Ownership

Ownership is a fundamental part of CobaltC's type and runtime model.

An owned value has exactly one responsible owner.

The owner is responsible for eventual destruction.

39. Move Semantics

A move transfers ownership. 

File a = open("data.txt")?;
File b = move a;

After the move, a MUST NOT be used as an owner of the transferred value.

A moved-from binding MAY remain in scope, but its moved value is unavailable except as permitted by explicitly defined partial-move rules.

40. Copy Semantics

A type may support copying.

Implicit copying is permitted only when the type's semantics explicitly permit it.

Copying produces an independent value according to the type's copy contract.

Copying is not ownership transfer.

41. Partial Moves

For aggregate values, an individual owned component MAY be moved independently when the compiler can track the resulting state.

A moved component cannot subsequently be used through its original ownership path.

Unaffected independent components MAY remain usable.

42. Borrowing

A borrow provides access to an owned value without transferring ownership. Borrowing does not create a new owner of the borrowed value.

CobaltC supports shared borrows and mutable borrows. A shared borrow provides read access to its referent (the thing being pointed to). A mutable borrow provides exclusive mutable access to its referent.

The managed pointer type T* represents a managed, non-null pointer. The expression &expr creates a shared borrow, and the expression &mut expr creates a mutable borrow when the applicable ownership and mutability rules permit the operation.

The fundamental borrowing rule is:

zero or more compatible shared borrows OR one mutable borrow

A shared borrow is compatible with another shared borrow when neither borrow provides conflicting access to the same storage. A mutable borrow is incompatible with any other borrow of the same storage that would permit conflicting access.

Conflicting borrows MUST be rejected.

String value = "hello";
String* pointer = &value;
print(*pointer);
print(value);

The borrow does not transfer ownership of value. The binding value remains the owner of the string.

A value MUST NOT be moved while a live borrow of that value would be invalidated by the move.

String value = "hello";
String* pointer = &value;
String moved = move value;
print(*pointer); // ERROR: `value` was moved while borrowed

A borrow MUST NOT outlive its referent. A managed pointer MUST NOT be used after the storage required by that pointer has ceased to be valid.

43. Shared Borrows

A shared borrow provides read access to its referent. Multiple compatible shared borrows MAY exist simultaneously.

String value = "hello";
String* first = &value;
String* second = &value;
print(*first);
print(*second);

Shared borrows MAY alias the same value when they provide only compatible shared access.

String value = "hello";
String* first = &value;
String* second = &value;
String* third = &value;
print(*first);
print(*second);
print(*third);

A shared borrow MUST NOT be used to perform mutable access to its referent.

String value = "hello";
String* pointer = &value;
append(*pointer, "!"); // ERROR: shared borrow does not permit mutation

A mutable borrow MUST NOT be created while an incompatible shared borrow remains live.

mut String value = "hello";
String* shared = &value;
String* mutable = &mut value; // ERROR: `value` is already borrowed
print(*shared);
append(*mutable, "!");

The implementation MUST permit multiple compatible shared borrows and MUST reject conflicting mutable access.

44. Mutable Borrows

A mutable borrow provides exclusive mutable access to its referent.

A mutable borrow requires a mutable owner or otherwise mutable storage as defined by the applicable type rules.

mut String value = "hello";
String* pointer = &mut value;
append(*pointer, " world");
print(*pointer);

While a mutable borrow is live, another mutable borrow of overlapping storage MUST NOT be created.

mut String value = "hello";
String* first = &mut value;
String* second = &mut value; // ERROR: conflicting mutable borrow
append(*first, "!");
append(*second, "?");

A mutable borrow MUST NOT coexist with a conflicting shared borrow.

mut String value = "hello";
String* shared = &value;
String* mutable = &mut value; // ERROR: conflicting borrow
print(*shared);
append(*mutable, "!");

A mutable pointer MAY subsequently be used for shared access when no conflicting mutable use of that pointer remains live.

mut String value = "hello";
String* mutable = &mut value;
append(*mutable, "!");
String* shared = mutable;
print(*shared);

Mutable access MUST remain exclusive for the duration of the applicable mutable borrow.

45. Borrow Lifetime

A borrow has a lifetime during which its managed pointer remains valid and the associated borrowing restrictions apply.

A borrow lifetime MUST NOT exceed the lifetime of its referent.

String* pointer;
{
    String value = "hello";
    pointer = &value;
    print(*pointer);
}
print(*pointer); // ERROR: `value` no longer exists

A borrow is live at a program point when a managed pointer derived from that borrow may subsequently be used and the borrow is therefore required to remain valid at that point.

A borrow MAY cease to be live before the end of its enclosing lexical scope when no subsequent use of a managed pointer derived from that borrow requires the borrow to remain live.

mut String value = "hello";
{
    String* pointer = &value;
    print(*pointer);
}
String* mutable = &mut value;
append(*mutable, " world");

The preceding program is valid because the shared borrow is no longer live when the mutable borrow is created.

The compiler MUST reject a program in which a managed pointer could be used after the lifetime of its referent has ended.

A borrow MUST remain valid across every operation in which the corresponding managed pointer is used.

46. Function Parameters and Returned Borrows

A function MAY accept a managed pointer as a parameter. Passing a managed pointer to a function provides access to the referenced value and does not transfer ownership.

fn length(String* value) : usize
{
    return length_of(*value);
}

String value = "hello";
usize size = length(&value);
print(value);
print(size);

A function MAY return a borrowed managed pointer when the returned pointer is guaranteed not to outlive its referent.

fn identity(String* value) : String*
{
    return value;
}

String value = "hello";
String* result = identity(&value);
print(*result);

When a returned managed pointer is derived from a borrowed parameter, the returned pointer MUST NOT outlive the source borrow.

fn first(String* value) : String*
{
    return value;
}

String value = "hello";
{
    String* result = first(&value);
    print(*result);
}

A function MUST NOT return a managed pointer to an ordinary local value whose lifetime ends when the function returns.

fn invalid() : String*
{
    String value = "hello";
    return &value; // ERROR: returned borrow outlives `value`
}

A function MAY return a managed pointer to storage whose lifetime is independently guaranteed to outlive the returned pointer.

CobaltC uses inferred borrow lifetimes. The compiler MUST determine whether parameter borrows, returned borrows, and the referenced storage satisfy the applicable lifetime and borrowing rules.

Ownership MUST NOT be inferred from a borrowed return value. Returning a managed pointer provides access to an existing value; it does not transfer ownership unless an explicitly defined ownership operation is used.

47. Reborrowing

A managed pointer MAY itself be borrowed. Such an operation is a reborrow.

A reborrow creates a new borrow whose access is derived from the existing managed pointer. Reborrowing MUST preserve the ownership, lifetime, and aliasing guarantees of the original borrow.

A mutable pointer MAY be temporarily reborrowed as a mutable pointer.

fn append_exclamation(String* value)
{
    append(*value, "!");
}

mut String value = "hello";
String* pointer = &mut value;
append_exclamation(&mut *pointer);
append(*pointer, "?");

While a conflicting reborrow is live, the original managed pointer MUST NOT be used in a conflicting manner.

mut String value = "hello";
String* pointer = &mut value;
String* reborrow = &mut *pointer;
append(*pointer, "!"); // ERROR: `pointer` is reborrowed
append(*reborrow, "?");

Once the reborrow is no longer live, the original managed pointer MAY be used again, subject to the ordinary borrowing rules.

Reborrowing does not transfer ownership of the underlying value.

48. Field and Partial Borrows

A field of a structure MAY be borrowed independently of another disjoint field.

struct Pair
{
    String first;
    String second;
}

mut Pair pair = { first: "one", second: "two" };
String* first = &mut pair.first;
String* second = &mut pair.second;
append(*first, "!");
append(*second, "?");

A borrow of one field does not, by itself, prevent access to a disjoint field.

mut Pair pair = { first: "one", second: "two" };
String* first = &mut pair.first;
append(pair.second, "!");
append(*first, "?");

Two field paths are disjoint when they identify distinct, non-overlapping storage within the same aggregate value.

The compiler MUST permit simultaneous borrows of fields that are established to be disjoint.

The compiler MUST reject simultaneous mutable borrows when the borrowed field paths may refer to overlapping storage.

mut Pair pair = { first: "one", second: "two" };
Pair* whole = &mut pair;
String* first = &mut pair.first;
use(*whole); // ERROR: conflicting borrow

A borrow of an entire aggregate conflicts with a mutable borrow of any overlapping part of that aggregate.

Partial borrowing MUST preserve the same aliasing, lifetime, and exclusivity guarantees as borrowing an entire value.

49. Aliasing

Aliasing occurs when more than one managed pointer provides access to the same underlying storage.

Multiple compatible shared managed pointers MAY alias the same storage.

String value = "hello";
String* first = &value;
String* second = &value;
print(*first);
print(*second);

A mutable managed pointer is exclusive. A mutable managed pointer MUST NOT coexist with another managed pointer that permits conflicting access to the same storage.

mut String value = "hello";
String* first = &mut value;
String* second = &mut value; // ERROR: mutable aliases are prohibited
append(*first, "!");
append(*second, "?");

For any storage location accessible through managed pointers, CobaltC MUST enforce the following invariant:

multiple compatible shared managed pointers OR one mutable managed pointer

A mutable managed pointer MUST NOT coexist with a conflicting shared managed pointer. Two mutable managed pointers MUST NOT provide conflicting access to the same storage.

shared shared shared

is therefore permitted when all managed pointers provide compatible shared access, while:

mutable mutable

and:

shared mutable

are prohibited when the managed pointers provide conflicting access to the same storage.

These aliasing requirements apply to direct managed pointers, reborrows, field borrows, function parameters, returned borrows, and collection element borrows.

Safe CobaltC operations MUST NOT provide a means to bypass these aliasing requirements.

50. Collection Borrowing

Elements of a collection MAY be borrowed when the collection operation and element type permit the corresponding access.

A shared element borrow provides shared access to the element.

Vector<i32> values = [10, 20, 30];
i32* first = &values[0];
i32* second = &values[1];
print(*first);
print(*second);

A mutable element MAY be borrowed when the collection and element permit mutable access.

mut Vector<i32> values = [10, 20, 30];
i32* first = &mut values[0];
*first = *first + 1;
print(values[0]);

A collection operation that requires mutable access MUST NOT occur while a conflicting borrow of the collection or of storage within the collection remains live.

mut Vector<i32> values = [10, 20, 30];
i32* first = &values[0];
values::push(&mut values, 40); // ERROR: conflicting borrow of `values`
print(*first);

If a collection operation may invalidate managed pointers to elements, the operation MUST NOT occur while such a pointer remains live.

An implementation MUST NOT permit a managed pointer to a collection element to be used after the underlying storage required by that pointer has ceased to be valid.

Collection-specific borrowing rules MAY impose additional restrictions where required to preserve ownership, lifetime, aliasing, or storage validity.

51. Borrow Invalidation

A managed pointer is valid only while its referent remains valid and the pointer satisfies the applicable borrowing rules.

An operation that conflicts with a live borrow MUST be rejected. A conflicting operation does not by itself make an otherwise valid managed pointer safe to use; the operation is prohibited while the conflicting borrow remains live.

A managed pointer MUST NOT be used after its referent has ceased to exist or after storage required by that pointer has ceased to be valid.

String* pointer;
{
    String value = "hello";
    pointer = &value;
}
print(*pointer); // ERROR: referent has been destroyed

A value MUST NOT be moved while a live borrow of that value would be invalidated by the move.

String value = "hello";
String* pointer = &value;
String moved = move value;
print(*pointer); // ERROR: `value` was moved while borrowed

A borrow MAY cease to restrict a value once the corresponding managed pointer is no longer used and the borrow is therefore no longer live.

mut String value = "hello";
{
    String* pointer = &value;
    print(*pointer);
}
append(value, " world");
print(value);

A collection operation that could invalidate an active element borrow MUST be rejected while that borrow remains live.

mut Vector<String> values = ["hello"];
String* pointer = &values[0];
values::push(&mut values, "world"); // ERROR: active element borrow
print(*pointer);

The compiler MUST reject a program when it can establish that a managed pointer would be used after its referent becomes invalid, or when an operation would violate the shared-borrow, mutable-borrow, lifetime, move, aliasing, or collection-borrowing rules.

52. Destruction

Owned values are destroyed deterministically.

An ownership responsibility is destroyed exactly once.

Moved-from ownership does not cause a second destruction.

53. Scope Destruction

For ordinary scope exit:

  • deferred blocks execute;
  • owned locals are destroyed in reverse declaration order;
  • control proceeds to the enclosing scope.

An implementation MUST preserve the observable consequences of this ordering.

54. Unwinding

If the implementation supports unwinding, scopes exited by supported unwinding MUST perform their specified destruction.

55. Abort

An abort terminates execution immediately.

Normal destruction is not guaranteed after an abort.

56. Nullability

Nullable values are explicitly represented by nullable types.

null cannot inhabit a non-nullable type.

Before dereferencing a nullable reference, the compiler MUST establish that it is non-null.

Flow-sensitive refinement is permitted.

57. Bounds Safety

Safe indexing MUST remain within valid bounds.

The compiler MAY eliminate runtime bounds checks when validity has been proven statically.

Unchecked indexing belongs to unsafe facilities.

58. Option<T>

CobaltC does not use Option because it introduces a Rust-style abstraction that is not necessary for CobaltC's C-like type system. Nullable pointers, enums, and ordinary values provide the required semantics without introducing a separate optional-value type.

59. Result<T,E>

The canonical recoverable-error type is: 

enum Result<T,E>
{
    Ok(T),
    Err(E)
}

Expected operational failures SHOULD be represented using Result.

60. Error Propagation

The ? operator propagates a compatible error from the current operation to the enclosing function.

It is not an exception mechanism.

61. Strings

String owns UTF-8 text storage.

Str represents borrowed UTF-8 text.

A valid text value MUST contain valid UTF-8.

Arbitrary bytes require byte-oriented APIs.

62. Vector<T>

Vector<T> owns dynamically allocated contiguous storage.

Its capacity MAY exceed its current length.

Operations that change storage in ways that could invalidate active references are governed by the borrowing rules.

63. Slices

A slice provides borrowed access to a contiguous range of elements in another value. A slice does not own the elements or the storage to which it refers.

A slice is therefore a non-owning view. Creating a slice does not copy the elements in the selected range, and destroying a slice does not destroy those elements.

Slices are immutable by default. A slice binding may be declared mut when mutable access to the elements in the slice is required. A mutable slice remains non-owning.

63.1 Slice Syntax

A slice is created using range syntax applied to a contiguous sequence. For a range of the form start..end, both the starting and ending indices are included. 

values[1..4]

The expression above creates a slice containing the elements at indices 1, 2, 3, and 4.

A range may omit its ending index using .... An omitted ending index means the final element of the sequence. 

values[1...]

The expression above creates a slice beginning at index 1 and continuing through the final element of values.

The entire sequence may be sliced using ... without a starting or ending index. 

values[...]

The expression above creates a slice containing every element of values.

The following forms are therefore defined:

Expression Meaning
values[1..4] Elements at indices 1 through 4, inclusive
values[1...] Element 1 through the final element
values[...] The entire sequence

The ... token in a slice range denotes the final element of the underlying sequence. It does not represent an arbitrary variadic or omitted expression in other contexts.

63.2 Slice Types

A slice type is written using Slice[T], where T is the element type. 

Slice[i32] values;
Slice[String] names;
Slice[Point] points;

A slice type does not imply ownership. The owner of the underlying storage remains responsible for the elements and their destruction.

An ordinary slice binding is immutable by default: 

Slice[i32] slice = values[1..4];

The elements may be read through slice, but they may not be modified through that binding. 

i32 value = slice[0];     // valid

slice[0] = 10;            // compile-time error

A mutable slice is declared by applying mut to the local binding: 

mut Slice[i32] slice = values[1..4];

slice[0] = 10;            // valid, subject to borrow checking

The mut qualifier applies to the binding's access capability. It does not give the slice ownership of the underlying elements or storage.

63.3 Slice Creation and Borrowing

Creating a slice creates a borrow of the selected range. It does not transfer ownership of the underlying value.

An immutable slice requires shared access to the selected range. 

i32[] values = ...;

Slice[i32] first_half = values[0..3];
Slice[i32] second_half = values[4..7];

In the example above, first_half refers to indices 0 through 3, while second_half refers to indices 4 through 7. The two ranges do not overlap.

Multiple immutable slices may exist simultaneously when permitted by the ordinary borrowing rules.

Creating a mutable slice requires exclusive mutable access to the selected range of the underlying value. 

mut i32[] values = ...;
mut Slice[i32] middle = values[2..6];

While middle is an active mutable borrow, conflicting shared or mutable borrows of the same elements are prohibited.

Two mutable slices may coexist when their ranges are disjoint and the borrowing rules can establish that they do not overlap.

63.4 Slice Bounds

A slice range must identify a valid range within the underlying sequence. For a sequence of length n, a non-empty range with an explicit ending index must satisfy: 

0 <= start <= end < n

Because both endpoints are included, n - 1 is the greatest valid index for a sequence of length n.

For example, if values contains eight elements, the following is valid: 

values[0..7]

and contains all eight elements.

The following is invalid because index 8 does not identify an element in an eight-element sequence: 

values[0..8]       // bounds violation

The exact handling of a bounds violation is determined by the language's bounds-checking rules.

An open-ended range of the form start... is valid when start identifies an element in the underlying sequence. It includes that element and every subsequent element through the final element.

The complete-range form ... selects every element in the underlying sequence.

63.5 Slice Length

The length associated function returns the number of elements accessible through a slice. It may be referenced using either the slice type or a value of that type. 

Slice[i32] slice = values[2..5];

usize count = slice::length(slice);

The slice above contains four elements, at indices 2, 3, 4, and 5. Therefore slice::length(slice) returns 4.

For a range start..end, the length of the resulting slice is: 

end - start + 1

For an open-ended range start..., the length is the number of elements from start through the final element of the underlying sequence.

The complete-range form values[...] has a length equal to the length of the underlying sequence.

63.6 Slice Element Access

Elements of a slice are accessed using ordinary indexing. 

Slice[i32] slice = values[2..5];

i32 first = slice[0];
i32 second = slice[1];

The index is relative to the beginning of the slice rather than the beginning of the underlying sequence. In the example above, slice[0] refers to values[2], and slice[1] refers to values[3].

For a slice of length length, a valid index satisfies: 

0 <= index < length

An index outside this range is a bounds violation.

63.7 Slice Lifetimes

The lifetime of a slice cannot exceed the lifetime of the storage to which it refers. A slice cannot be returned from a function, stored in another value, or otherwise retained in a manner that would allow it to outlive the underlying storage.

A slice does not keep its underlying owner alive merely by existing. Ownership remains with the original owning value.

Destroying or otherwise invalidating the underlying storage while a slice referring to that storage is active is prohibited.

63.8 Slices and Ownership

Passing a slice to a function passes borrowed access rather than ownership of the elements. 

fn sum(Slice[i32] values) : i32
{
    i32 total = 0;
    usize index = 0;

    while index < Slice[i32]::length(values)
    {
        total = total + values[index];
        index = index + 1;
    }

    return total;
}

A function receiving a slice does not become responsible for destroying the elements in that slice.

63.9 Mutable Slices

A mutable slice provides exclusive mutable access to the elements in its range. 

fn set_first(mut Slice[i32] values, i32 value)
{
    values[0] = value;
}

Calling a function with a mutable slice requires the caller to provide the exclusive mutable access required by the borrow checker. 

mut Slice[i32] slice = values[1..4];

set_first(slice, 42);

A mutable slice does not transfer ownership of its elements. When the mutable borrow ends, ownership remains with the original owner.

63.10 Slices and Reallocation

A slice refers to the current storage of its owner. If an operation relocates that storage, a slice referring to the old storage would no longer be valid.

Consequently, an operation that may reallocate or otherwise invalidate the storage underlying an active slice is prohibited while that slice is active.

For example, a slice into an array or Vector prevents a conflicting operation that could relocate or otherwise invalidate its elements: 

i32[] values = ...;

Slice[i32] view = values[1...];

// An operation that may invalidate `values` while `view` is active
// is prohibited by the borrowing rules.

This rule applies regardless of whether the slice is immutable or mutable. A mutable slice additionally imposes the exclusive-access requirements described above.

63.11 Slice Destruction

A slice is non-owning. Destroying a slice ends the borrow represented by that slice but does not destroy the elements to which it refers.

The owner of the underlying storage remains responsible for destroying those elements according to the ordinary ownership and destruction rules.

63.12 Slice and Range Semantics

Slice ranges use inclusive endpoints. A range of the form start..end includes both start and end. 

values[0..3]

therefore selects the elements at indices 0, 1, 2, and 3.

The number of elements in such a range is: 

end - start + 1

= 3 - 0 + 1
= 4

The open-ended form: 

values[1...] // from index 1 through the final valid index

selects the element at index 1 and every subsequent element through the final element of values.

The complete-range form: 

values[...] // from index 0 through the final valid index

selects every element in the sequence.

The important distinction is that ... means "through the final valid element", not "one past the end.

The ... token in these forms specifically denotes the end of the sequence.

64. Box<T>

CobaltC intentionally keeps its pointer model small and C-like. Ownership, borrowing, lifetime, and thread-safety are properties enforced by the language rather than by a family of smart-pointer types.

CobaltC does not use Box because dynamically allocated objects are represented using ordinary C-style pointers, with ownership and lifetime tracked by the language rather than encoded in a separate pointer type.

65. Rc<T>

CobaltC does not use Rc because reference-counted shared ownership is not part of its core pointer model; CobaltC instead uses ordinary pointers with statically enforced ownership and borrowing rules.

66. Arc<T>

CobaltC does not use Arc because thread-safe shared ownership through atomic reference counting is not a primitive of the language; cross-thread pointer use is governed by CobaltC's ownership, borrowing, and concurrency rules instead.

67. Weak<T>

CobaltC does not use Weak because it is specifically tied to reference-counted ownership; without Rc or Arc, weak references are unnecessary as a distinct pointer type.

68. Threads

CobaltC supports concurrent execution through threads.

A value transferred to another thread MUST satisfy the required ownership and thread-transfer constraints.

A thread MUST NOT retain an ordinary borrow to a local value that can cease to exist before the borrow is used.

69. Synchronization

Not applicable.

70. Mutex

A mutex provides exclusive synchronized access.

A lock guard maintains the ownership of the lock while the guard is live.

Destroying the guard releases the lock.

71. RwLock

Not applicable.

72. Atomics

Atomic operations are indivisible according to the specified atomic type and memory-order semantics.

Atomicity does not itself establish ownership or higher-level synchronization.

73. Channels

Not applicable.

74. Data Races

Safe CobaltC code MUST NOT contain an ordinary unsynchronized data race.

The language does not guarantee freedom from logical concurrency errors such as deadlocks or livelocks.

75. Memory Model

The memory model defines the ordering guarantees of synchronization and atomic operations.

Implementations MAY reorder operations internally provided observable behavior remains consistent with the language's memory model.

76. Unsafe Code and Functions

Unsafe operations require an explicit unsafe context, established either through an unsafe block or an unsafe function declaration: 

unsafe
{
    ...
}

unsafe fn some_function()
{
    ...
}

Marking a function as unsafe permits it to contain unsafe operations and indicates to callers that calling the function requires an enclosing unsafe context or block.

Unsafe permits operations requiring programmer-supplied invariants.

It does not make an invalid operation intrinsically correct.

77. Raw Memory

Raw-pointer dereference, unchecked memory manipulation and manual allocation/deallocation are unsafe facilities.

An implementation MUST NOT treat arbitrary raw memory as automatically satisfying CobaltC's type, lifetime or ownership requirements.

78. Safe Abstractions over Unsafe Code

Unsafe implementation code MAY be encapsulated by a safe API.

Such an API is valid only if its implementation maintains all invariants promised by its safe interface.

79. Foreign Functions

Foreign functions require explicit declarations.

The baseline foreign ABI is the C ABI.

Foreign functions are not assumed to obey CobaltC ownership, lifetime or safety rules.

80. FFI Ownership

Ownership crossing an FFI boundary MUST be defined by the API contract.

Possible contracts include:

  • borrowed for call duration
  • caller transfers ownership
  • callee transfers ownership
  • caller retains ownership
  • foreign runtime owns value

The ABI alone does not determine ownership.

81. ABI Profiles

A target ABI profile specifies at minimum:

  • architecture
  • operating system
  • pointer width
  • endianness
  • alignment
  • calling conventions
  • C ABI mapping
  • atomic capabilities
  • runtime model

Binary compatibility is guaranteed only where compatible ABI profiles are used.

82. Runtime

A hosted CobaltC program begins through main.

The runtime provides the facilities required by the language and standard library, including:

  • allocation;
  • destruction;
  • process integration;
  • I/O;
  • concurrency;

83. Allocation

Managed allocation must either produce a valid allocation or produce the specified allocation failure.

An implementation MUST NOT expose an invalid managed object as the result of failed allocation.

98.2 Managed Pointer and Lifetime Terminology

CobaltC uses the managed-pointer notation defined in Section 14:

T*
T*?

T* represents a managed, non-null pointer.

T*? represents a nullable managed pointer.

CobaltC does not expose explicit lifetime parameters as part of the 1.0.0 source-language syntax.

Lifetime information is inferred by the compiler as specified by Sections 18 and 45-47.

Accordingly, the following are equivalent concepts for purposes of the static model:

* the lifetime of a borrow;
* the interval during which a managed pointer remains valid; and
* the set of program points at which the borrowing relationship must remain established.

An implementation MAY represent these relationships internally using region variables, constraints, graphs, or another equivalent representation.

Such internal representations MUST NOT become additional CobaltC source syntax.

98.2.1 Lifetime Ordering

Where the compiler determines that one borrow must remain valid for at least as long as another borrow, the compiler MAY represent that relationship internally as a lifetime containment or outlives constraint.

For example, if a returned `T*` is derived from an input `T*`, the returned reference MUST NOT remain usable after the source borrow becomes invalid.

No explicit lifetime annotation is required from the programmer.

98.2.2 Lifetime Inference

The compiler MUST infer sufficient lifetime information to determine whether:

* a managed pointer outlives its referent;
* a returned managed pointer outlives the borrow from which it was derived;
* a borrow conflicts with another borrow;
* a move invalidates a live managed pointer;
* a collection operation invalidates an active managed pointer; or
* a managed pointer is used after the storage on which it depends ceases to be valid.

If the compiler cannot establish the required lifetime relationship, it MUST reject the program.

The compiler MUST NOT assume that an unproven lifetime relationship is valid merely because the referenced memory happens to remain allocated in a particular implementation.

98.3 Borrow Lifetime End Points

Section 45 permits a borrow to cease being live before the end of its lexical scope.

For purposes of this rule, a borrow is considered live when a subsequent operation may require the associated reference to remain valid or when the borrowing restrictions associated with that reference remain necessary.

A compiler MAY determine that a borrow has ended when it can prove that no subsequent operation can use the reference in a manner requiring the borrow to remain active.

This is an analysis rule, not a requirement that the implementation expose borrow lifetime information to the programmer.

The compiler MUST remain conservative when it cannot establish that a borrow has ended.

98.4 Managed Pointer Compatibility

The type compatibility rules for managed pointers are those already established by Sections 14, 16, 17, 42-47, and the applicable function and generic rules.

A managed pointer MUST retain the semantic distinctions associated with:

* nullability;
* mutability;
* ownership;
* borrowing; and
* lifetime.

An implementation MUST NOT treat two managed-pointer types as interchangeable merely because their machine representation is identical.

In particular:

T*

MUST NOT implicitly become:

T*?

or vice versa where doing so would violate the nullability rules.

Likewise, an implementation MUST NOT use representation-level pointer compatibility to bypass CobaltC's ownership or borrowing rules.

98.5 Dynamic Indexing and Borrow Checking

Collection operations involving dynamic indexes remain subject to the ordinary borrowing, aliasing, lifetime, and collection-borrowing rules.

For an operation such as:

values[i]

the compiler MUST determine whether the access is compatible with all active borrows.

If an operation may access storage that overlaps an active incompatible borrow, the operation MUST be rejected unless the compiler can establish that the accesses are in fact disjoint.

The compiler MAY use any sound internal representation to establish disjointness, including:

* field paths;
* index information;
* range information;
* control-flow analysis;
* symbolic constraints; or
* implementation-specific alias analysis.

The representation used by the compiler is not part of the CobaltC language.

98.5.1 Unknown Dynamic Aliasing

If two dynamic accesses cannot be proven disjoint, the compiler MAY conservatively treat them as potentially overlapping.

For example, where two mutable accesses depend on runtime indexes and the compiler cannot prove that the indexes identify distinct storage, it MUST NOT assume that they are disjoint merely because the programmer expects them to be.

This rule follows directly from the aliasing and mutable-borrow requirements of Sections 42-50.

98.6 Generic Type Checking

Generic declarations are statically checked according to Section 19.

A compiler MAY perform generic checking in multiple implementation phases.

For example, an implementation MAY:

  1. parse and construct an internal representation of the generic declaration;
  2. substitute concrete types at an instantiation;
  3. perform additional type and ownership checking for the instantiated form; and
  4. generate target code.

These phases are implementation details.

CobaltC 1.0.0 does not require a particular generic implementation strategy.

98.7 `Result` and the `?` Operator

The canonical recoverable-error type is the `Result<T,E>` type defined in Section 59.

The `?` operator is defined by Section 60 as error propagation.

For purposes of static reasoning, an expression of the form:

expression?

may be understood as performing the equivalent logical operation of:

1. evaluating `expression`;
2. determining whether the result represents success or failure;
3. continuing with the successful value; or
4. returning the compatible error from the current function.

The exact lowering is implementation-defined provided the observable behavior conforms to Section 60.

The `?` operator MUST NOT be treated as a panic, exception, or implicit unwinding mechanism.

A recoverable `Result` failure and an unrecoverable panic are distinct mechanisms.

98.8 Panic and Unwinding

CobaltC does not define a panic or exception-unwinding mechanism. An implementation MAY use internal unwinding or other mechanisms for its own purposes, but such mechanisms MUST NOT introduce additional CobaltC source-language semantics or observable behavior beyond that specified by CobaltC.

98.9 Concurrency Safety

Section 68 requires values transferred between threads to satisfy the applicable ownership and thread-transfer constraints.

Section 69 requires synchronization for shared mutable state.

These requirements are semantic requirements of CobaltC and do not require particular source-level marker traits or interfaces.

An implementation MAY internally classify types according to whether they may safely be transferred between threads or accessed concurrently.

Such classifications MAY be derived from:

* the type's fields;
* ownership properties;
* borrowing properties;
* synchronization types;
* atomic types;
* implementation-defined runtime properties; or
* other sound static analysis.

The internal classification MUST produce behavior consistent with Sections 68-75.

98.9.1 Thread Transfer

A value transferred to another thread MUST satisfy all ownership and lifetime requirements applicable to the transfer.

An ordinary borrow of a local value MUST NOT be transferred to a thread if the referent may cease to exist before the borrow can no longer be used.

An implementation MUST reject such a transfer when the required lifetime cannot be established.

98.9.2 Synchronization

The existence of shared ownership does not by itself provide synchronization.

In particular, reference-counted ownership does not permit unsynchronized conflicting mutation.

Shared mutable state MUST continue to obey the synchronization requirements of Sections 69-74.

98.10 Diagnostics and Source Locations

A conforming compiler MUST reject programs that violate normative static rules, as specified by Section 88.

The compiler SHOULD associate diagnostics with useful source locations.

An implementation MAY internally represent source locations using a structure containing information such as:

* source file identity;
* starting position;
* ending position;
* line number; and
* column number.

The exact internal representation is not normative.

98.10.1 Error Recovery

A compiler MAY continue parsing after a syntax error in order to report additional diagnostics.

Error recovery MUST NOT cause the compiler to accept a program that violates a normative syntax or semantic rule.

A compiler MAY synchronize at tokens such as:

;
}

or at declaration boundaries such as:

fn
struct

provided that the recovery strategy does not alter the interpretation of a conforming program.

No additional keyword is implied by the use of a token as an error-recovery boundary.

In particular, `let` is not a CobaltC 1.0.0 keyword.

98.11 Layout and ABI

The CobaltC source-language semantics do not require a particular internal representation of managed references.

An implementation MAY represent a managed reference using a machine pointer or another representation appropriate to the target, provided that the representation preserves all required CobaltC semantics.

The representation of a managed reference MUST NOT cause the implementation to bypass:

* lifetime checking;
* ownership checking;
* nullability checking;
* borrowing rules; or
* aliasing rules.

98.11.1 Aggregate Layout

Aggregate layout is determined by the applicable ABI profile described in Section 81.

An implementation MUST document implementation-defined layout properties where required by that profile.

The CobaltC 1.0.0 specification does not require all aggregates to use the layout rules of any particular compiler, intermediate representation, or target architecture.

98.11.2 Foreign Functions

The baseline foreign ABI is the C ABI, as specified by Section 79.

An `extern` declaration and its associated ABI behavior MUST conform to the applicable ABI profile.

The ABI does not by itself determine ownership.

Ownership crossing an FFI boundary MUST continue to be defined by the API contract as specified by Section 80.

98.12 Module and Name Resolution

CobaltC 1.0.0 uses the module syntax defined in Section 8:

module example;

and imports modules using:

import io;
import io { print, println };

These forms are normative.

An implementation MUST NOT replace them with an alternative module declaration or import syntax while claiming that the alternative syntax is standard CobaltC 1.0.0.

Module names establish namespaces. Name resolution is lexical and module-aware. An unresolved name is a compile-time error.

An implementation MAY map modules to source files, directories, packages, compilation units, or another internal representation, provided that the resulting module and name-resolution behavior conforms to Section 8 and this section.

98.12.1 Module Exports and API Contracts

Declarations describe implementation. The export block describes the module's external contract.

The export block applies only to declarations belonging to the module in which the block appears.

A submodule is a separate module and is not exported by its parent module.

If a module does not contain an export block, the module exports no declarations.

A declaration at module scope is not externally accessible merely because it exists in the module. A declaration is externally accessible only if its name is included in the module's export block.

Any declaration not listed in the export block is a module-local implementation detail. Such declarations MAY be added, removed, renamed, reorganized, or otherwise changed without constituting an API-breaking change, provided that the exported interface and its specified semantics remain compatible.

CobaltC 1.0.0 does not define declaration-level visibility modifiers such as public, private, or protected.

98.12.2 Export Declarations

A module MAY contain an export block listing the names of declarations that are made available to importing modules. The export block lists names only; the declarations remain in the defining module.

module hash;

export
{
    HashTable;
    hash_create;
    hash_insert;
    hash_remove;
}

struct HashTable
{
    ...
}

fn hash_create(...) : HashTable *
{
    ...
}

fn hash_insert(...)
{
    ...
}

fn resize(...)
{
    ...
}

In this example, HashTable, hash_create, hash_insert, and hash_remove form the external contract of the module. resize and any other declaration not listed in the export block are implementation details.

98.12.3 Exported Types

Exporting a type makes the type name available to external code but MUST NOT make the representation of that type available to external code.

External code MAY name an exported type, use the type in function signatures, and pass or return values or pointers to the type, subject to the normal rules of the type system.

External code MUST NOT directly inspect, access, or manipulate the representation of an exported type. In particular, external code MUST NOT access fields, layout, or other representation details of an exported type unless those details are explicitly exposed by a language mechanism defined by this specification.

The defining module controls how an exported type is constructed, accessed, and manipulated through its exported declarations.

module hash;

export
{
    HashTable;
    hash_create;
    hash_insert;
    hash_remove;
}

struct HashTable
{
    usize capacity;
    ...
}

fn hash_create(...) : HashTable *
{
    ...
}

fn hash_insert(HashTable *table, Key key, Value value)
{
    ...
}

fn hash_remove(HashTable *table, Key key)
{
    ...
}

fn resize(HashTable *table)
{
    ...
}

External code MAY therefore use the exported interface:

HashTable *table = hash_create(...);

hash_insert(table, key, value);
hash_remove(table, key);

but MUST NOT directly access the internal representation of HashTable.

When a struct type is exported by a module, all its associated functions of that type are implicitly exported and need not be listed separately in the module's export block.

98.12.4 API Stability

The export block defines the source-level API boundary of a module.

Changes to declarations that are not exported MUST NOT constitute API-breaking changes. An implementation MAY change internal algorithms, reorganize implementation code, rename internal declarations, add or remove internal declarations, or change the representation of an exported type without requiring dependent modules to change, provided that the exported interface and its specified semantics remain compatible.

The export block therefore serves as both an access boundary and an explicit declaration of the module's contractual surface.

98.12.5 Submodules

A module MAY have one or more submodules. A submodule is a distinct module with its own namespace, declarations, imports, and export block.

A submodule is identified by a qualified module name consisting of its parent module name followed by the submodule name, separated by a period.

module graphics.math;

The module graphics.math is a submodule of graphics.

Each submodule defines its own external contract independently. Declarations exported by a submodule are not automatically exported by its parent module.

For example:

module graphics.math;

export
{
    Vec2;
    dot;
}

struct Vec2
{
    f64 x;
    f64 y;
}

fn dot(Vec2 a, Vec2 b) : f64
{
    ...
}

External code MAY import the submodule directly:

import graphics.math;

and MAY use declarations exported by graphics.math according to the normal rules of name resolution.

The existence of graphics.math does not make its declarations available through graphics. A parent module MUST NOT be considered to export declarations from a submodule merely because the submodule exists.

Submodules MAY themselves have further submodules, subject to the same rules.

98.12.6 Module Hierarchy and Encapsulation

Module hierarchy is a namespace and organization mechanism and MUST NOT implicitly grant access to declarations between parent and child modules.

A declaration that is not exported by its defining module remains inaccessible to other modules, including parent modules, sibling modules, and child modules, unless another language rule explicitly provides access.

For example, the following modules have independent contracts:

module graphics;

export
{
    render;
}
module graphics.math;

export
{
    Vec2;
    dot;
}
module graphics.backend;

export
{
    Backend;
}

The parent-child relationship between these modules does not by itself make declarations in one module accessible to another.

To use declarations from graphics.math, external code imports graphics.math directly:

import graphics.math;

Likewise, declarations exported by graphics are available only through the normal import and name-resolution rules for graphics.

This preserves the module export principle throughout the module hierarchy: declarations describe implementation, while each module's export block describes its external contract.

98.12.7 Translation Units and Modules

A translation unit MUST define exactly one module.

The module declaration of a translation unit establishes the module defined by that translation unit. A translation unit MUST NOT contain more than one module declaration.

Submodules are distinct modules and therefore MUST be defined by separate translation units.

An implementation MAY use any source-file or compilation-unit organization internally, provided that the resulting module behavior conforms to this specification.

98.12.8 Rationale

CobaltC deliberately does not require public, private, protected, or equivalent visibility attributes on individual declarations.

Visibility is instead expressed at the module boundary. Declarations describe the implementation, while the export block describes the contract offered by the module.

This design preserves CobaltC's C-like simplicity while providing a strong software-engineering boundary: anything not in export is free to change without being an API-breaking change, provided that the specified semantics of the exported interface remain compatible.

The export list also provides a single, explicit description of a module's external interface rather than requiring readers to discover its API by inspecting visibility attributes throughout the implementation.

The same principle applies to submodules. A module hierarchy provides organization and namespaces, but does not weaken encapsulation. Each module explicitly controls its own external contract, and submodules are imported independently by their qualified module names.

An implementation MAY provide additional visibility mechanisms as extensions, but such mechanisms MUST be distinguishable from standard CobaltC behavior and MUST NOT silently alter the semantics of a valid CobaltC 1.0.0 program.

98.13 Structs and Associated Functions

This section clarifies the semantics of associated functions defined in Section 25.

CobaltC 1.0.0 defines a struct as a data type whose declaration describes its data representation. A struct declaration MUST NOT contain method or member-function declarations.

Functions operating on a struct are ordinary functions and MAY be declared independently of the struct declaration. A function MAY accept a struct value, pointer, or reference as an argument and MAY return a struct value, pointer, or reference, subject to the normal rules of the type system.

CobaltC 1.0.0 does not define an implicit this, self, or equivalent receiver parameter for functions operating on a struct.

98.13.1 Ordinary Struct Functions

A function MAY operate on a struct without being associated with that type. Such a function is an ordinary function and is declared using the normal function declaration syntax.

For example:

struct HashTable { usize capacity; } fn hash_insert(HashTable *table, Key key, Value value) { ... }

In this example, hash_insert is an ordinary function. It is not associated with or a member of HashTable.

The caller MUST provide the HashTable argument explicitly:

hash_insert(&table, key, value);

98.13.2 Associated Functions

A function MAY be associated with a struct by using the Type::function declaration syntax:

fn HashTable::hash_insert(HashTable *table, Key key, Value value) { ... }

An associated function is an ordinary function with a type-qualified name. Association provides type-oriented organization and lookup but does not make the function a member of the struct or introduce an implicit receiver.

All parameters of an associated function MUST be declared explicitly. Association does not alter the function's parameter list, calling convention, ownership, borrowing, or return-value semantics.

An associated function MAY therefore be declared without a parameter referring to its associated type:

fn HashTable::new(usize capacity) : HashTable { ... }

An associated function MAY also explicitly accept a value, pointer, or reference to its associated type:

fn HashTable::insert(HashTable *table, Key key, Value value) { ... }

98.13.3 Qualified Names and Calls

An associated function MAY be referenced through its associated type using a type-qualified name:

HashTable::new(100); HashTable::insert(&table, key, value);

For a generic type, the type arguments form part of the qualification:

Stack<i32>::new(); Stack<i32>::push(&stack, 10);

An associated function MAY also be referenced through a value whose statically known type is the associated type:

mut Stack<i32> stack = Stack<i32>::new();
stack::push(&stack, 10);
stack::push(&stack, 20);
stack::push(&stack, 30);

When an associated function is referenced through a value, the compiler determines the associated type from the value's statically known type and performs associated-function lookup on that type. The value used for qualification is not implicitly passed to the function.

Consequently, if stack has type Stack<i32>, the following calls identify the same associated function:

Stack<i32>::push(&stack, 10); stack::push(&stack, 10);

In both calls, &stack is an explicit argument because the selected function declares the corresponding parameter.

The :: operator qualifies a function name with a type or value for associated-function lookup. It does not imply an implicit receiver or alter the function's declared parameter list. The . operator remains field access and MUST NOT introduce implicit method lookup or invocation.

The number and types of arguments supplied in a call MUST satisfy the selected function's signature. A function with a return type other than void MUST return a value compatible with its declared return type. A void function MUST NOT return a value.

98.13.4 Associated Functions and Ordinary Functions

An operation on a struct MAY be implemented either as an ordinary function or as an associated function. The two forms have the same fundamental function semantics; association determines how the function is named and discovered.

For example, the following declarations define equivalent forms of an operation:

fn Stack_push(Stack *stack, i32 value) { ... } fn Stack::push(Stack *stack, i32 value) { ... }

The associated form does not constitute a separate function model and does not introduce object-oriented method dispatch or implicit receiver semantics.

98.13.5 Constructors and Factory Functions

An associated function is not required to operate on an existing value of its associated type. It MAY create and return a new value.

For example:

Stack<i32> stack = Stack<i32>::new();

Because new has no receiver parameter, it MAY be called through the associated type without an existing Stack<i32> value.

CobaltC does not treat new as a special constructor mechanism. It is an ordinary associated function whose declared return type determines the value produced by the call.

98.13.6 Modules and External Interfaces

Ordinary functions and associated functions MAY be declared within the same module as the types on which they operate. A module MAY use its export block to define which types and ordinary functions form its external interface.

Exporting a type implicitly exports its associated functions. An associated function therefore need not be listed separately in the module's export block.

98.13.7 Associated Function Identity and Name Resolution

An associated function is identified by its associated type and function name.

Associated functions with the same function name MAY exist for different types and are distinct functions. For example, Stack::push and HashTable::push identify different associated functions:

fn Stack::push(Stack *stack, i32 value) { ... } fn HashTable::push(HashTable *table, i32 value) { ... }

An ordinary function and an associated function MAY also have the same unqualified function name:

fn push(i32 value) { ... } fn Stack::push(Stack *stack, i32 value) { ... }

These declarations identify distinct functions. An unqualified call refers only to an ordinary function:

push(10);

A type-qualified call refers to the associated function of the specified type:

Stack::push(&stack, 10);

A value-qualified call uses the statically known type of the qualifying value to determine the associated type:

stack::push(&stack, 10);

The existence of an ordinary function with the same unqualified name MUST NOT cause it to be selected by a type-qualified or value-qualified associated-function call. Likewise, the existence of an associated function MUST NOT cause it to be selected by an unqualified call.

Qualification determines whether ordinary-function or associated-function lookup is performed. Once an associated function has been selected, its declared parameter list determines whether the call is valid.

98.13.8 Rationale

CobaltC deliberately keeps struct declarations focused on the representation of data and does not introduce method or member-function declarations within structures.

Functions remain ordinary functions, making their parameters, return values, calling conventions, ownership, and borrowing behavior explicit. The Type::function syntax provides type-oriented organization and lookup without introducing implicit this or self parameters or object-oriented method semantics.

Value-qualified lookup provides a concise alternative when an existing value is available. The qualifying value determines the static type used for lookup but is passed to the selected function only when it is explicitly supplied as an argument.

The result is a programming model that retains the explicitness of C-like functions while allowing APIs to be organized naturally around their associated types.

98.17 Collection Borrowing Clarification

Collection types such as `Vector<T>` are subject to the ordinary borrowing and invalidation requirements.

An operation that may reallocate, resize, move, or otherwise invalidate storage MUST NOT be performed while an active reference would be invalidated by that operation.

For example:

mut Vector<String> values = ["hello"];
String* reference = &values[0];

values::push(&mut values, "world"); // ERROR if this operation may invalidate `reference`

print(*reference);

The compiler MUST reject an operation when it can establish that the operation invalidates a live reference.

An implementation MAY permit an operation when it can establish that the operation cannot invalidate the particular reference involved.

The implementation MAY use static or runtime techniques to establish this fact, provided that safe programs retain the guarantees required by the specification.

98.18 Destruction and Ownership Clarification

An owned value has one responsible ownership path unless its type explicitly provides shared ownership.

A move transfers the relevant ownership responsibility.

A moved-from binding MUST NOT cause a second destruction of the moved value.

For aggregate values, partial moves are valid only where the compiler can independently track the moved and remaining components.

At scope exit, the destruction ordering specified by Section 53 remains authoritative:

1. deferred blocks execute;
2. owned locals are destroyed in reverse declaration order; and
3. control proceeds to the enclosing scope.

An implementation MAY use a different internal mechanism to achieve this behavior.

98.19 Nullability Clarification

A nullable managed pointer is represented using:

T*?

A non-null managed pointer is represented using:

T*

A nullable pointer MUST NOT be dereferenced until the compiler has established that it is non-null.

The compiler MAY perform flow-sensitive nullability refinement.

For example, after a condition that establishes that a `T*?` value is not null, subsequent operations within the proven region MAY treat the value as non-null for purposes of dereference checking.

Such refinement MUST NOT outlive the condition that establishes it if later control flow can invalidate the proof.

98.20 Bounds Checking Clarification

Safe indexing MUST remain within valid bounds.

A compiler MAY eliminate a runtime bounds check when it can prove statically that the index is valid.

This optimization MUST preserve the observable semantics of the program.

The compiler MUST NOT eliminate a required bounds check merely because an out-of-bounds access is unlikely.

Unchecked indexing and equivalent unchecked memory operations remain unsafe facilities.

98.21 Unsafe Code Boundary

Unsafe operations remain subject to the explicit `unsafe` context defined by Section 76.

An unsafe context permits operations for which the programmer is responsible for maintaining additional invariants.

It does not change the meaning of safe CobaltC.

In particular, placing an operation inside `unsafe` MUST NOT cause safe operations elsewhere in the program to lose their specified ownership, lifetime, nullability, bounds, or concurrency guarantees.

Unsafe code MAY establish abstractions that are subsequently exposed through safe interfaces only when those interfaces preserve their documented invariants.

* region-based lifetime inference;

* control-flow graphs;
* path-sensitive alias analysis;

* generic specialization;
* pointer-based managed-reference representations;
* LLVM;

An implementation MAY use these techniques individually or in combination.

No implementation technique becomes part of the CobaltC language merely because an implementation uses it.

98.23 Identifier Security and Unicode Restrictions

3. Vector Interface and Implementation Boundary

Section 62 specifies that Vector<T> owns dynamically allocated contiguous storage, that its capacity may exceed its length, and that operations capable of invalidating references are governed by the ordinary borrowing rules. The specification intentionally does not prescribe the internal representation or allocation strategy.

The Vector<T> implementation below is deliberately separated from the conformance program. The specification defines Vector<T> semantically as an owning contiguous collection, but it does not prescribe a particular allocation, raw-storage, or destruction implementation. Consequently, the implementation is non-normative and should not be interpreted as defining additional CobaltC source-language facilities.

The implementation must also ensure that any collection operation capable of relocating elements must not be permitted while a live managed pointer exists whose validity depends on the collection's current storage. This follows from the collection borrowing and borrow-invalidation rules.

A raw-storage implementation must distinguish the lifetime of the allocation from the lifetime of the values stored within it. Allocated storage does not, by itself, constitute a collection of live T values. Likewise, releasing raw storage must not result in a second destruction of values whose ownership has already been moved.

The following module is assuming the low-level allocator API is spelled allocate(n) / deallocate(ptr, n) and returns Result. 

module std.vector;

import std.result;

export
{
    Vector;
    VectorPushError;
    VectorPopError;
}


enum VectorPushError
{
    AllocationFailed,
    CapacityOverflow
}


enum VectorPopError
{
    Empty
}


struct Vector<T>
{
    // The representation of Vector is intentionally implementation-defined.
    //
    // A conforming implementation MUST maintain:
    //
    //     0 <= len <= capacity
    //
    // The Vector owns exactly the live T values in [0, len).
    //
    // data is null when capacity == 0.
    //
    // Access to data is performed only within unsafe code.

    data: raw T*;
    len: usize;
    capacity: usize;
}


// Grows the Vector so that it can hold at least required elements.
//
// This function is private to the module.
//
// The Vector is unchanged if allocation fails or the required capacity
// cannot be represented.
fn Vector<T>::grow(Vector<T>* vector, usize required) : Result<void, VectorPushError>
{
    if (required <= vector->capacity)
    {
        return Ok;
    }

    usize new_capacity = vector->capacity;

    if (new_capacity == 0)
    {
        new_capacity = 1;
    }

    while (new_capacity < required)
    {
        // Prevent capacity multiplication from wrapping.
        if (new_capacity > usize::MAX / 2)
        {
            new_capacity = required;
            break;
        }

        new_capacity = new_capacity * 2;
    }

    // Prevent the element count from overflowing the allocation size.
    if (new_capacity > usize::MAX / sizeof(T))
    {
        return Err(VectorPushError::CapacityOverflow);
    }

    unsafe
    {
        Result<raw T*, AllocationError> allocation = allocate<T>(new_capacity);

        if (allocation.is_err())
        {
            return Err(VectorPushError::AllocationFailed);
        }

        raw T* new_data = allocation.unwrap();

        usize i = 0;

        while (i < vector->len)
        {
            new_data[i] = move vector->data[i];
            i = i + 1;
        }

        if (vector->data != null)
        {
            deallocate<T>(vector->data, vector->capacity);
        }

        vector->data = new_data;
        vector->capacity = new_capacity;
    }

    return Ok;
}


// Creates an empty Vector.
//
// No storage is allocated.
fn Vector<T>::new() : Vector<T>
{
    return Vector<T>
    {
        data: null,
        len: 0,
        capacity: 0
    };
}


// Returns the number of live elements.
fn Vector<T>::len(Vector<T>* vector) : usize
{
    return vector->len;
}


// Returns the number of allocated T slots.
fn Vector<T>::capacity(Vector<T>* vector) : usize
{
    return vector->capacity;
}


// Returns true when the Vector contains no elements.
fn Vector<T>::is_empty(Vector<T>* vector) : bool
{
    return vector->len == 0;
}


// Appends value to the Vector.
//
// On success, ownership of value is transferred to the Vector.
//
// If allocation fails or capacity overflows, the Vector and value
// remain unchanged.
fn Vector<T>::push(Vector<T>* vector, T value) : Result<bool, VectorPushError>
{
    if (vector->len == vector->capacity)
    {
        if (vector->len == usize.MAX)
        {
            return Err(VectorPushError::CapacityOverflow);
        }

        usize required = vector->len + 1;

        Result<void, VectorPushError> result = Vector<T>::grow(vector, required);

        if (result.is_err())
        {
            return Err(result.unwrap_err());
        }
    }

    unsafe
    {
        vector->data[vector->len] = move value;
    }

    vector->len = vector->len + 1;

    return Ok(true);
}


// Removes and returns the final live element.
//
// On success, ownership of the element is transferred to the caller.
//
// If the Vector is empty, returns Err(Empty).
fn Vector<T>::pop(Vector<T>* vector) : Result<T, VectorPopError>
{
    if (vector->len == 0)
    {
        return Err(VectorPopError::Empty);
    }

    vector->len = vector->len - 1;

    unsafe
    {
        return Ok(move vector->data[vector->len]);
    }
}


// Returns a borrowed pointer to the element at index.
//
// The language's normal bounds rules reject index >= len.
//
// The returned managed pointer borrows the element from the Vector.
fn Vector<T>::get(Vector<T>* vector, usize index) : T*
{
    unsafe
    {
        return &vector->data[index];
    }
}


// Removes and destroys every live element.
//
// Allocated storage is retained.
fn Vector<T>::clear(Vector<T>* vector)
{
    usize i = 0;

    while (i < vector->len)
    {
        unsafe
        {
            T::destroy(&vector->data[i]);
        }

        i = i + 1;
    }

    vector->len = 0;
}


// Ensures that the Vector has capacity for at least
// len + additional elements.
//
// If sufficient capacity already exists, nothing is done.
//
// If allocation fails or capacity overflows, the Vector remains unchanged.
fn Vector<T>::reserve(Vector<T>* vector, usize additional)
    : Result<void, VectorPushError>
{
    if (additional > usize.MAX - vector->len)
    {
        return Err(VectorPushError::CapacityOverflow);
    }

    usize required = vector->len + additional;

    return Vector<T>::grow(vector, required);
}


// Reduces the Vector's length to new_len.
//
// Elements removed from the Vector are destroyed exactly once.
//
// Allocated storage is retained.
//
// The language's bounds rules reject new_len > len.
fn Vector<T>::truncate(Vector<T>* vector, usize new_len)
{
    if (new_len >= vector->len)
    {
        return;
    }

    usize i = new_len;

    while (i < vector->len)
    {
        unsafe
        {
            T::destroy(&vector->data[i]);
        }

        i = i + 1;
    }

    vector->len = new_len;
}


// Removes the element at index.
//
// Elements following index are moved toward the beginning.
//
// The language's bounds rules reject index >= len.
fn Vector<T>::remove(Vector<T>* vector, usize index) : T
{
    unsafe
    {
        T removed = move vector->data[index];

        usize i = index;

        while (i + 1 < vector->len)
        {
            vector->data[i] = move vector->data[i + 1];
            i = i + 1;
        }

        vector->len = vector->len - 1;

        return removed;
    }
}


// Removes the element at index without preserving order.
//
// If index is not the final element, the final element is moved
// into the removed element's position.
//
// The language's bounds rules reject index >= len.
fn Vector<T>::swap_remove(Vector<T>* vector, usize index) : T
{
    unsafe
    {
        usize last = vector->len - 1;

        T removed = move vector->data[index];

        if (index != last)
        {
            vector->data[index] = move vector->data[last];
        }

        vector->len = last;

        return removed;
    }
}


// Inserts value before index.
//
// index == len is equivalent to push.
//
// On success, ownership of value is transferred to the Vector.
//
// If allocation fails or capacity overflows, the Vector and value
// remain unchanged.
//
// The language's bounds rules reject index > len.
fn Vector<T>::insert(Vector<T>* vector, usize index, T value) : Result<void, VectorPushError>
{
    if (index == vector->len)
    {
        Result<bool, VectorPushError> result = Vector<T>::push(vector, move value);

        if (result.is_err())
        {
            return Err(result.unwrap_err());
        }

        return Ok;
    }

    Result<void, VectorPushError> result = Vector<T>::reserve(vector, 1);

    if (result.is_err())
    {
        return result;
    }

    unsafe
    {
        usize i = vector->len;

        while (i > index)
        {
            vector->data[i] = move vector->data[i - 1];
            i = i - 1;
        }

        vector->data[index] = move value;
    }

    vector->len = vector->len + 1;

    return Ok;
}


// Attempts to reduce capacity to len.
//
// If len is zero, the allocation is released.
//
// If len is non-zero, a new allocation of exactly len elements
// is created and the live elements are moved into it.
//
// If allocation fails, the Vector remains unchanged.
fn Vector<T>::shrink_to_fit(Vector<T>* vector) : Result<void, VectorPushError>
{
    if (vector->len == vector->capacity)
    {
        return Ok;
    }

    if (vector->len == 0)
    {
        unsafe
        {
            if (vector->data != null)
            {
                deallocate<T>(vector->data, vector->capacity);
            }
        }

        vector->data = null;
        vector->capacity = 0;

        return Ok;
    }

    if (vector->len > usize.MAX / sizeof(T))
    {
        return Err(VectorPushError::CapacityOverflow);
    }

    unsafe
    {
        Result<raw T*, AllocationError> allocation = allocate<T>(vector->len);

        if (allocation.is_err())
        {
            return Err(VectorPushError::AllocationFailed);
        }

        raw T* new_data = allocation.unwrap();

        usize i = 0;

        while (i < vector->len)
        {
            new_data[i] = move vector->data[i];
            i = i + 1;
        }

        deallocate<T>(vector->data, vector->capacity);

        vector->data = new_data;
        vector->capacity = vector->len;
    }

    return Ok;
}


// Destroys the Vector and all elements it owns.
//
// Every live element is destroyed exactly once.
//
// The backing allocation is then released.
//
// The compiler/runtime invokes this operation when the Vector's
// owning lifetime ends.
fn Vector<T>::destroy(Vector<T>* vector)
{
    usize i = 0;

    while (i < vector->len)
    {
        unsafe
        {
            T::destroy(&vector->data[i]);
        }

        i = i + 1;
    }

    unsafe
    {
        if (vector->data != null)
        {
            deallocate<T>(vector->data, vector->capacity);
        }
    }

    vector->data = null;
    vector->len = 0;
    vector->capacity = 0;
}

Vector<T>::push transfers ownership of value into the Vector when the operation succeeds. On success it returns Ok(true). On failure, the Vector remains unchanged and the returned VectorPushError identifies the failure.

Vector<T>::pop transfers ownership of the final element back to the caller. If the Vector is empty, it returns Err(VectorPopError::Empty).

The bool success payload used by push is intentional. push returns Result<bool, VectorPushError>, so successful completion is represented by Ok(true).

4. Stack Example

module stack_example;

import std.result;
import std.io { println };
import std.vector;


enum StackError
{
    Empty,
    AllocationFailed,
    CapacityOverflow
}


struct Stack<T>
{
    Vector<T> values;
}


// `new` is an ordinary associated function. It has no implicit
// receiver and takes no arguments.
fn Stack<T>::new() : Stack<T>
{
    return Stack<T>
    {
        values = Vector<T>::new()
    };
}


// `push` takes an explicit mutable pointer to the Stack.
// The value is transferred to the Vector on successful insertion.
fn Stack<T>::push(Stack<T>* stack, T value) : Result<bool, StackError>
{
    return match Vector<T>::push(&mut stack.values, value)
    {
        Ok(inserted) => Ok(inserted),

        Err(VectorPushError::AllocationFailed) =>
            Err(StackError::AllocationFailed),

        Err(VectorPushError::CapacityOverflow) =>
            Err(StackError::CapacityOverflow)
    };
}


// `pop` takes an explicit mutable pointer to the Stack and transfers
// ownership of the removed value to the caller.
fn Stack<T>::pop(Stack<T>* stack) : Result<T, StackError>
{
    return match Vector<T>::pop(&mut stack.values)
    {
        Ok(value) => Ok(value),

        Err(VectorPopError::Empty) =>
            Err(StackError::Empty)
    };
}


// `is_empty` requires only shared access because it does not mutate
// the Stack or its Vector.
fn Stack<T>::is_empty(Stack<T>* stack) : bool
{
    return Vector<T>::len(&stack.values) == 0;
}


// Destroys the Stack and the Vector it owns.
//
// Vector destruction destroys all live elements and releases the
// Vector's backing storage.
fn Stack<T>::destroy(Stack<T>* stack)
{
    Vector<T>::destroy(&mut stack.values);
}


fn run_stack(Stack<i32>* stack) : Result<bool, StackError>
{
    // The successful Result carries a bool.
    bool pushed = Stack<i32>::push(stack, 10)?;

    // `pushed` is initialized before it is read.
    if pushed
    {
        i32 value = Stack<i32>::pop(stack)?;
        println("popped value: {}", value);
    }

    // This operation fails because the Stack is now empty.
    //
    // `?` propagates StackError::Empty to the caller.
    Stack<i32>::pop(stack)?;

    return Ok(true);
}


fn main() : i32
{
    // `mut` applies to the local binding. It permits the binding to
    // be mutably borrowed; it does not change the Stack type itself.
    mut Stack<i32> stack = Stack<i32>::new();

    match run_stack(&mut stack)
    {
        Ok(completed) =>
        {
            if completed
            {
                println("stack operation completed");
            }
        },

        Err(StackError::AllocationFailed) =>
            println("failed to allocate storage"),

        Err(StackError::CapacityOverflow) =>
            println("stack capacity limit reached"),

        Err(StackError::Empty) =>
            println("stack is empty")
    }

    return 0;
}

With the standard-library implementation providing the declared Vector<T> operations, the example has the following intended observable output: 

popped value: 10
stack is empty

Semantics Visible in the Example

The example intentionally exercises several of the normative semantic rules established by the CobaltC 1.0.0 specification. It is not intended to exercise the complete language or complete conformance suite. Section 92 requires a conformance suite to contain multiple positive and negative tests covering the language as a whole; one example cannot substitute for that suite.

Modules, Visibility, and Types

  • Modules and Imports: Each source module begins with a single module declaration and imports declarations from other modules using the standard CobaltC import syntax.
  • Export Visibility: The supporting modules use explicit export blocks. Declarations not listed in an export block remain module-local.
  • Generic Nominal Types: Result<T, E>, Vector<T>, and Stack<T> are generic nominal types. The concrete example instantiates Stack<i32>.
  • Opaque Exported Representation: An exported Vector<T> hides its representation from importing modules. External code uses its exported operations rather than directly manipulating its internal storage.

Functions and Call Semantics

  • Associated Functions: Functions such as Stack<T>::new, Stack<T>::push, and Stack<T>::pop use type-qualified associated-function syntax.
  • No Implicit Receiver: Associated functions do not receive an implicit this or self parameter. A function operating on an existing Stack explicitly declares its pointer parameter.
  • Explicit Arguments: The receiver-like object is passed explicitly, for example Stack<i32>::push(&mut stack, 10). Type qualification selects the associated function; it does not manufacture an implicit argument.
  • Ordinary Constructor Function: Stack<T>::new() is an ordinary associated function that takes no arguments and returns a newly constructed Stack<T>.

Ownership, Borrowing, and Lifetimes

  • Ownership: The local stack owns its Stack<i32> value, and the Stack owns its Vector<i32>. The Vector is responsible for the values it contains.
  • Mutable Borrowing: &mut stack provides mutable access to the Stack without transferring ownership. The mutable borrow is required for operations that modify the Stack.
  • Field Borrowing: &mut stack.values borrows the Vector field directly. The field-borrowing rules permit such access where the relevant storage is disjoint from conflicting borrows.
  • Shared Borrowing: Stack<T>::is_empty and Vector<T>::len require only shared access because they do not modify their referents.
  • Move Semantics: A successful push transfers ownership of the supplied value to the Vector, while a successful pop transfers ownership of the removed value to the caller.
  • Deterministic Destruction: Owned values are destroyed deterministically according to the scope and ownership rules. A moved-from ownership responsibility does not cause a second destruction.
  • Borrow Invalidation: A concrete Vector implementation that relocates its elements must not permit a managed pointer to an element to remain usable after the storage on which that pointer depends has ceased to be valid.

Error Handling and Propagation

  • Result-Based Errors: Fallible operations use Result<T, E> with the defined Ok(T) and Err(E) variants.
  • No Unit-Valued Result: The example deliberately does not use Result<void, E> or Ok. The specification defines void as a function return type and does not define () as a CobaltC value; tuples are explicitly absent from the language.
  • Error Translation: Stack<T>::push and Stack<T>::pop translate the Vector error types into the Stack-level error type using exhaustive pattern matching.
  • Error Propagation: The ? operator propagates compatible errors from run_stack rather than acting as an exception or panic mechanism.
  • Exhaustive Matching: The matches over VectorPushError, VectorPopError, and StackError enumerate every variant of the corresponding enum.

Collections and Memory Safety

  • Vector Ownership: Vector<T> owns its dynamically allocated contiguous storage and the live values contained within its logical range.
  • Length and Capacity: The Vector invariant is 0 <= len <= capacity. Capacity may exceed length.
  • Reallocation: A Vector implementation may change its storage when additional capacity is required. Such an operation is subject to the ordinary borrowing and lifetime rules.
  • Unsafe Boundary: Raw pointer manipulation and manual allocation/deallocation are unsafe facilities. A concrete standard-library implementation may encapsulate them behind a safe Vector interface, provided the implementation maintains the invariants promised by that interface.
  • Implementation Freedom: The specification does not require a particular representation, allocation algorithm, growth factor, or compiler-generated destruction mechanism. Those are implementation details provided that the specified observable semantics are preserved.

Associated and Ordinary Functions

Associated functions and ordinary functions use the same underlying function semantics. The difference is that an associated function has a type-qualified name and participates in associated-function lookup.

For example, Stack<T>::push is declared as an ordinary function associated with Stack<T>: 

fn Stack<T>::push(Stack<T>* stack, T value)
{
    Vector<T>::push(&mut stack.values, value);
}

The associated function may be referenced using its qualified type name: 

Stack<i32>::push(&mut stack, 10);

It may also be referenced through a value whose statically known type is Stack<i32>: 

stack::push(&mut stack, 10);

In both cases, qualification selects the associated function, while the function's declared parameter list determines the arguments that must be supplied.

Neither associated-function form introduces an implicit this, self, or equivalent receiver parameter. The value-qualified form uses stack to determine the associated type, but does not implicitly pass stack to the function.

Conformance Status of the Example

The stack_example portion is intended as a positive source-level example of the specified language constructs. The std.vector implementation sketch is intentionally non-normative because the current CobaltC 1.0.0 specification does not define source-level raw allocation, raw-storage initialization, or explicit destruction primitives.

The formatting syntax used by println is a standard-library facility rather than part of the core CobaltC grammar. A {} sequence in a println format string is a format placeholder and consumes the next formatting argument from left to right. The number of {} placeholders must exactly equal the number of formatting arguments; a mismatch is a compile-time error. For example, println("x = {}, y = {}", x, y) is valid, while supplying either too many or too few formatting arguments is invalid. A format string containing no placeholders may be used without formatting arguments.

Accordingly, this section demonstrates conformance to selected language rules; it does not constitute a complete conformance suite. A complete conformance suite must separately test lexical and syntactic behavior, name resolution, typing, initialization, ownership, moves, copying, borrowing, lifetimes, destruction, nullability, bounds, patterns, generics, Result, collections, strings, concurrency, unsafe boundaries, runtime behavior, FFI, ABI requirements, diagnostics, and regressions.

AI functions exceptionally well as a force multiplier—acting as a junior compiler engineer that can crank out thousands of lines of parser code - but a human architect is still required to design and solve the hard semantic machinery.

A word of warning: When an AI hits an ambiguous semantic edge case, it typically hallucinates a naive solution that breaks down under rigorous validation.

If you were to leverage AI to create a production-ready implementation of the CobaltC language specification (incorporating recent errata and memory invariants), a structured, phased execution plan is essential to prevent context degradation and ensure correctness.

Phase 1: Frontend and AST Generation
  • Lexer and Parser: Instruct the AI to generate a recursive-descent parser (or grammar definition using tools like Lark or Pest) conforming strictly to CobaltC's lexical rules, case sensitivity, and block structures.
  • AST Structuring: Direct the AI to define a comprehensive Abstract Syntax Tree (AST) covering nominal types (structs, enums), arrays, type aliases, and explicit memory modifier keywords.
Phase 2: Semantic Analysis and Type Checking
  • Symbol Resolution: Build a scoping and name-resolution pass to map declarations, functions, and module boundaries.
  • Strict Type Constraints: Implement type-checking logic enforcing CobaltC's foundational semantic invariants - specifically ensuring that implicit conversions never silently strip nullability, violate mutability, or alter lifetime guarantees.
Phase 3: The Static Analysis & Borrow Subsystem
  • Lifetime and Ownership Tracking: Because the specification permits intricate patterns like dynamic collection element borrowing, task the AI with building a constraint-based region inference engine.
  • Borrow-Checker Logic: Program rules to validate that references (T*, T*?) do not outlive their owners, tracking explicit ownership transfers and argument compatibility at every function call boundary.
Phase 4: Target Lowering and Code Generation
  • IR Lowering Pass: Direct the AI to write a translation pass converting the type-checked AST into an intermediate representation, targeting LLVM IR or Cranelift.
  • ABI and Layout Resolution: Define platform-specific layout rules, struct padding, alignment, and calling conventions since the specification leaves these mechanical choices to the implementor.
Phase 5: Iterative Test-Driven Implementation
  • Incremental Prompting: Feed the specification to the AI module by module (syntax first, then type checking, then memory safety) rather than passing the entire document at once to prevent context degradation.
  • Negative Test Generation: Have the AI generate a suite of test cases containing intentional spec violations (such as illegal implicit nullability stripping or lifetime violations) to iteratively validate the generated compiler's error-reporting accuracy.
