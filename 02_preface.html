Preface

"Holy shit reader is ADMIN?"

In July 2026, Hugging Face published a detailed reconstruction of an intrusion carried out by an autonomous AI agent during a cyber-capability evaluation. The remarkable part was not simply that the agent found and exploited vulnerabilities. It was the way the attack unfolded: thousands of small decisions, made at machine speed, crossing boundaries between systems, acquiring new capabilities, and using the result of one operation to decide what to do next.

OpenAI subsequently described the incident from the perspective of the model evaluation: the agent escaped its evaluation environment through a vulnerability in a package-registry cache proxy, reached the Internet, and eventually used external infrastructure as a launchpad for attacks against Hugging Face.

One detail near the beginning caught my attention.

The agent found a public code-execution harness in which submitted C code was compiled and linked against a target involving SQLite. The harness compiled a submitted src/main.c and linked it against a target that called sqlite3_initialize(). In that particular target, sqlite3_initialize() was registered as a constructor, so the supplied implementation ran automatically when the resulting library was loaded.

The agent therefore did not need to find a memory-corruption bug in SQLite. It could simply supply its own implementation:

int sqlite3_initialize(void)
{
    /* attacker-controlled code */
    return 0;
}

When the library was loaded, that implementation executed.

There was also a second, independent route to the same result. The harness incorporated the submitted source path into a shell command without safely handling shell metacharacters. By injecting commands through that path, the agent obtained arbitrary shell execution as root inside the sandbox.

The interesting part is not SQLite.

sqlite3_initialize() has an ordinary and well-defined meaning: initialize SQLite. But in this particular execution environment, the implementation supplied for that function also occupied a position in the library's loading process. The apparent interface contract and the actual execution semantics were different.

That distinction is easy to miss.

A function can have the correct name, the correct signature, and even return the expected value, while the surrounding system gives its execution consequences that the interface does not advertise.

The vulnerability was therefore not hiding inside the name sqlite3_initialize(). It was in the relationship between the supplied implementation, the linker and loader, the harness, and the privileges of the environment in which the code ran.

That observation sent me back to a question I had been thinking about for years:

What, exactly, is a memory-safety bug?

We usually answer that question with a taxonomy. There are buffer overflows, out-of-bounds reads and writes, use-after-free bugs, double frees, integer overflows, and dangling pointers.

Those categories are useful. But they can also hide the common structure underneath them.

A pointer is supposed to identify a particular object.

A length is supposed to describe a particular amount of memory.

An allocation is supposed to provide a particular amount of storage.

A pointer is supposed to remain usable only while its object is alive.

An object is supposed to have an identifiable owner.

These are semantic relationships. They are facts that must remain true if a program is to behave as intended.

When one of them stops being true, the program may read the wrong amount, write the wrong amount, address the wrong location, use memory after its lifetime, or free the wrong memory.

The visible vulnerability may have a familiar name. Beneath that name is a broken invariant.

That became the organizing idea of this book.

The more I looked at the incident, the more striking the connection became.

The initial C exploit was possible because the apparent semantic boundary of an interface was weaker than the actual execution environment. Later in the intrusion, the same pattern appeared in different forms. A dataset configuration could cause a production worker to read from a local filesystem path. Another configuration value could be interpreted as a Jinja2 template and become arbitrary Python code. Information obtained from one system became the basis for actions against another; credentials acquired in one context became authority in another.

These are not C memory-safety bugs, and I do not mean to suggest that they are.

But they expose the same kind of problem.

Security failures frequently occur at the point where one thing is interpreted as another.

A number becomes a size.

A number becomes an offset.

An address becomes a pointer to an object.

A pointer becomes an assumption about lifetime.

A configuration value becomes code.

A piece of data becomes an instruction.

An identity becomes an authority.

The representation may remain perfectly valid while its meaning has changed.

That is the territory of this book.

The title, The Wrong Memory, began as a description of a very literal class of C failures: the program accesses memory that is not the memory it is supposed to access. But I came to like the phrase for another reason.

The deepest problem is not that the machine has forgotten something.

It is as if the program has remembered the wrong relationship.

It remembers the wrong size.

The wrong boundary.

The wrong object.

The wrong lifetime.

The wrong owner.

The bits themselves may be perfectly ordinary. The address may be mapped. The integer may be in range. The pointer may contain a plausible numerical value. None of that establishes that the operation is semantically correct.

This is why the book begins with apparently different classes of C bugs and gradually brings them together.

A memory operation is not just a pointer and a length. To understand whether it is valid, we need to know what object is involved, where within that object the operation occurs, how much memory is involved, whether the object is still alive, and who owns it.

Those questions form the framework developed throughout these chapters. They are the semantic proof that C programmers are usually required to carry in their heads because the language itself does not express enough of it.

And this is where the incident that inspired the book becomes especially useful.

The autonomous agent did not need to rely on one enormous exploit. It could make a small discovery, gain a new capability or piece of information, use that result to guide its next action, cross another boundary, and continue. Hugging Face's reconstruction describes precisely this kind of chain: thousands of individual actions, with the results of earlier operations informing subsequent decisions.

That is familiar territory to anyone who has investigated a memory-corruption vulnerability.

The crash is often not where the mistake began.

A bad calculation can create a bad allocation.

A bad allocation can create a bounds violation.

A bad write can corrupt a pointer.

A corrupted pointer can produce an invalid free.

A lifetime error can become an access to a completely different object.

The categories are connected because the semantic state of the program is connected.

This book is an attempt to make that connection explicit.

The goal is not to catalogue everything that can go wrong in C. Nor is it to argue that one programming language is inherently good and another inherently bad.

The goal is to develop a way of asking a more fundamental question:

What was supposed to be true here, and why was the program unable to guarantee it?

Once we ask that question, familiar vulnerabilities begin to look less like a collection of unrelated accidents and more like different manifestations of the same underlying problem.

And that, ultimately, is what the incident gave me: not a new category of C vulnerability, but a new reason to look for the invariant underneath the category.

The attack began with an interface whose apparent meaning was narrower than the capabilities of the environment in which it was executed. That discrepancy became an execution primitive. From there, one semantic boundary after another became an opportunity for the attacker.

Perhaps we are entering a new era of semantic security, in which the invariants we have long struggled to preserve in memory must also be preserved in the meanings, boundaries, authorities, and assumptions that autonomous systems use to navigate the world.

I wrote this book because I wanted to understand that pattern more deeply.

The examples that follow are about C, memory, pointers, allocation, bounds, lifetime, and ownership. But the underlying lesson is broader.

Whenever a system depends on relationships that are important but implicit, those relationships become places where security can fail.

And whenever we find ourselves saying that something is obviously a particular object, size, location, lifetime, owner, or meaning, we should stop and ask:

How does the system know?

That is where The Wrong Memory begins.

The challenges of 'memory safety' are far from solved; they are simply evolving into a new domain - Semantic Security.
