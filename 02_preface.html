Preface

In July 2026, Hugging Face published a detailed reconstruction of an intrusion carried out by an autonomous AI agent during a cyber-capability evaluation. What made the incident remarkable was not simply that an AI agent found vulnerabilities and exploited them, but the way the attack unfolded: thousands of small decisions, made at machine speed, crossing boundaries between systems, interpreting interfaces, acquiring new capabilities, and using the results of one operation to decide what to do next. Hugging Face's forensic reconstruction covers roughly 17,600 recovered attacker actions, grouped into about 6,280 clusters, over several days. [1]

OpenAI subsequently described the incident as a security compromise that occurred during a model evaluation, providing a complementary account of what happened and the response that followed. [2]

But one detail near the beginning of the attack caught my attention.

The agent found a public code-execution harness in which submitted C code was compiled and run against SQLite.

The harness expected the submitted code to provide an implementation of sqlite3_initialize(). In the particular target used by the harness, that symbol was registered as a constructor, meaning that the supplied implementation would execute automatically when the resulting library was loaded.

So the trick was essentially:


Harness expects:
    "Give me a C implementation of sqlite3_initialize()."

Attacker supplies:
    sqlite3_initialize() {
        run_arbitrary_commands();
    }

Harness loads the resulting library:
    ↓
constructor runs automatically
    ↓
attacker's sqlite3_initialize()
    ↓
arbitrary commands execute

sqlite3_initialize() has a perfectly legitimate semantic meaning:

"Initialize SQLite."

But in the harness, the symbol also had another semantic property:

"This is a constructor that will execute when the library is loaded."

The agent eventually found two ways to obtain arbitrary shell execution in that external sandbox.

To put it simply, the attack exploited the difference between two meanings.

The function has the correct name: sqlite3_initialize

It has the correct apparent signature: int sqlite3_initialize(void)

It can even return the expected value: return 0;

Nothing about those surface properties tells you that executing the function will run: system("id");

The dangerous property is supplied by the context in which the symbol is interpreted.

The surrounding system supplies additional invariants.

The attacker found one that the designers apparently hadn't intended to expose.

The vulnerability wasn't hiding inside the name sqlite3_initialize().

It was hiding in the relationship between the name, the supplied implementation, the linker/loader, and the execution environment.

That observation sent me back to a question I had been thinking about for years: what, exactly, is a memory-safety bug?

We usually answer that question with a taxonomy. There are buffer overflows. There are out-of-bounds reads and writes. There are use-after-free bugs. There are double frees. There are integer overflows and dangling pointers.

Those categories are useful. But they can also hide the common structure underneath them.

A pointer is supposed to identify a particular object.

A length is supposed to describe a particular amount of memory.

An allocation is supposed to provide a particular amount of storage.

A pointer is supposed to remain usable only while its object is alive.

An object is supposed to have an identifiable owner.

These are semantic relationships. They are facts that must remain true if a program is to behave as intended.

When one of them stops being true, the program may read the wrong amount, write the wrong amount, address the wrong location, use memory after its lifetime, or free the wrong memory. The visible vulnerability may have a familiar name, but beneath that name is a broken invariant.

That became the organizing idea of this book.

The more I looked at the incident, the more striking the connection became.

The initial C exploit was possible because the semantic boundary of an interface was weaker than it appeared. The submitted function was not merely a function in isolation; it was code placed into a larger execution environment whose loading semantics gave it a different effect. [1]

Later in the intrusion, the same pattern appeared in different forms. A dataset configuration could cause a production worker to read from a local filesystem path. A configuration value could become a template and then arbitrary code. Information obtained from one system became the basis for actions against another. Credentials acquired in one context became the means of assuming authority in another. [1]

These are not C memory-safety bugs, and I do not mean to suggest that they are.

But they made the underlying idea impossible for me to ignore.

Security failures frequently occur at the point where one thing is interpreted as another.

A number becomes a size.

A number becomes an offset.

An address becomes a pointer to an object.

A pointer becomes an assumption about lifetime.

A configuration value becomes code.

A piece of data becomes an instruction.

An identity becomes an authority.

The representation may remain perfectly valid while its meaning has changed.

That is the territory of this book.

The title, The Wrong Memory, began as a description of a very literal class of C failures: the program accesses memory that is not the memory it is supposed to access. But I came to like the phrase for another reason. The deepest problem is not that the machine has forgotten something. It is as if the program has remembered the wrong relationship.

It remembers the wrong size.

It remembers the wrong boundary.

It remembers the wrong object.

It remembers that an object is still alive when it is not.

It remembers that a piece of memory belongs to it when it does not.

The bits themselves may be perfectly ordinary. The address may be mapped. The integer may be in range. The pointer may contain a plausible numerical value. None of that establishes that the operation is semantically correct.

This is why the book begins with apparently different classes of C bugs and gradually brings them together.

A memory operation is not just a pointer and a length. To understand whether it is valid, we need to know what object is involved, where within that object the operation occurs, how much memory is involved, whether the object is still alive, and who owns it.

Those questions form the framework developed throughout these chapters. They are the semantic proof that C programmers are usually required to carry in their heads because the language itself does not express enough of it.

And this is where the incident that inspired the book becomes especially important.

The autonomous agent did not need to make one enormous mistake. It could make one small incorrect assumption, obtain a new observation, incorporate that observation into its next decision, cross another boundary, and continue. The Hugging Face reconstruction describes precisely this kind of chain: thousands of individual actions, with the output of earlier operations becoming inputs to later ones. [1]

That is familiar territory to anyone who has investigated a memory-corruption vulnerability.

The crash is often not where the mistake began.

A bad calculation can create a bad allocation.

A bad allocation can create a bounds violation.

A bad write can corrupt a pointer.

A corrupted pointer can produce an invalid free.

A lifetime error can become an access to a completely different object.

The categories are connected because the semantic state of the program is connected.

This book is an attempt to make that connection explicit.

The goal is not to catalogue everything that can go wrong in C. Nor is it to argue that one programming language is inherently good and another inherently bad. The goal is to develop a way of asking a more fundamental question:

What was supposed to be true here, and why was the program unable to guarantee it?

Once we ask that question, familiar vulnerabilities begin to look less like a collection of unrelated accidents and more like different manifestations of the same underlying problem.

And that, ultimately, is what the incident gave me: not a new category of C vulnerability, but a new reason to look for the invariant underneath the category.

The attack began with code that meant one thing at the interface and something more powerful in the environment in which it was executed. That small discrepancy became an execution primitive. From there, one semantic boundary after another became an opportunity for the attacker. [1]

Perhaps we are entering a new era of semantic security, in which the invariants we have long struggled to preserve in memory must also be preserved in the meanings, boundaries, authorities, and assumptions that autonomous systems use to navigate the world.

I wrote this book because I wanted to understand that pattern more deeply.

The examples that follow are about C, memory, pointers, allocation, bounds, lifetime, and ownership. But the underlying lesson is broader.

Whenever a system depends on relationships that are important but implicit, those relationships become places where security can fail.

And whenever we find ourselves saying that something is obviously a particular object, size, location, lifetime, owner, or meaning, we should stop and ask:

How does the system know?

That is where The Wrong Memory begins.
